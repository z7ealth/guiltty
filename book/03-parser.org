#+TITLE: The parser: bytes in, commands out
#+STARTUP: overview

* Syntax, not meaning

Bash, =ls= and =less= send a mix of text and *control sequences*.
[[file:../lib/guiltty/parser.ex][Guiltty.Parser]] only works out the *shape* of each sequence and turns it into
a command. What a command *does* is the job of [[file:../lib/guiltty/terminal.ex][Guiltty.Terminal]] (next
chapter). Keeping them apart means the parser never needs to change when
guiltty learns a new sequence.

| Bytes                       | Command                              |
|-----------------------------+--------------------------------------|
| printable ASCII run         | ={:print, "ls"}=                     |
| =\r=                        | =:cr=                                |
| =\n=, VT, FF                | =:lf=                                |
| =\b=, =\t=                  | =:bs=, =:ht=                         |
| BEL (=\a=, byte 7)          | =:bell= (chapter 24)                 |
| =ESC [ 1 ; 31 m=            | ={:csi, nil, [1, 31], "", ?m}=       |
| =ESC [ ? 25 l=              | ={:csi, ??, [25], "", ?l}=           |
| =ESC [ 38 : 2 : : 255 : 0 : 0 m= | ={:csi, nil, [[38, 2, nil, 255, 0, 0]], "", ?m}= |
| =ESC M=, =ESC ( B=          | ={:esc, "", ?M}=, ={:esc, "(", ?B}=  |
| =ESC ] 0 ; title BEL=       | ={:osc, "0;title"}=                  |
| =ESC P ... ESC \=           | (dropped: DCS)                       |
| UTF-8 text                  | ={:print, "señor 日本"}= (chapter 13) |

* The anatomy of a CSI sequence

ECMA-48 defines every CSI ("Control Sequence Introducer") sequence the same
way, whatever it means:

#+begin_example
   ESC [   ?        1 ; 31          SP            m
   -----   ------   -----------     -----------   -----
   CSI     private  parameters      intermediates final byte
           marker   0x30-0x3F       0x20-0x2F     0x40-0x7E
           < = > ?  digits ; :                    picks the function
#+end_example

- The *final byte* says what to do: =m= is SGR (colors), =H= moves the cursor,
  =J= erases.
- *Parameters* are numbers separated by =;=. An empty one (=ESC [ ; 5 H=)
  means "use the default", and is =nil= here. =:= separates
  *sub-parameters* inside one parameter: =38:2::255:0:0= is a single
  parameter, a 24-bit color, kept together as a list.
- A *private marker* (=?= mostly) means "not in the standard": =ESC [ ? 25 l=
  is a DEC extension (hide the cursor).
- *Intermediates* are rare: =ESC [ 2 SP q= sets the cursor shape.

* The state machine

This is Paul Williams' parser for DEC terminals (vt100.net), the de facto
model every modern terminal follows. Each byte moves the parser between
states:

#+begin_example
                       printable -> print
                       C0        -> execute
                 +--------+
          +----->| ground |<-----------------------------------------+
          |      +--------+                                          |
          |          | ESC                                           |
          |          v                                               |
          |      +--------+  0x20-2F  +---------------------+  final |
          |      | escape |---------->| escape_intermediate |--------+
          |      +--------+           +---------------------+  esc_dispatch
          |       |  |  |  final 0x30-7E -> esc_dispatch ------------+
          |     [ |  |  +-------------------------------+            |
          |       v  | ] P X ^ _                        |            |
          |  +-----------+                              v            |
          |  | csi_entry |                     +---------------+     |
          |  +-----------+                     | osc_string /  |     |
          |   |  |     |                       | ignored_string|--ST-+
          |   |  |     | digits ; : < = > ?    +---------------+
          |   |  |     v
          |   |  |  +-----------+  0x20-2F  +------------------+
          |   |  |  | csi_param |---------->| csi_intermediate |
          |   |  |  +-----------+           +------------------+
          |   |  |     | final                 | final
          |   |  |     v                       v
          +---|--+-- csi_dispatch <------------+
              |
              +-- malformed (e.g. "?" after digits) -> csi_ignore -> final -> ground
#+end_example

Three rules apply in every state except the strings:

- *ESC* always starts a new sequence, abandoning the current one.
- *CAN* and *SUB* (=0x18=, =0x1A=) abort the sequence and go back to ground.
- *Other C0 controls are executed right away*, even in the middle of a
  sequence: =ESC [ 1 CR 2 H= performs the CR and then moves to row 12. Real
  terminals behave this way, so we do too.

Strings are different: inside an OSC everything up to BEL or ST (=ESC \=)
is data. DCS, SOS, PM and APC strings are swallowed whole for now.

* Limits

Anything the parser stores comes from a program you might not trust (try
=cat= on a random file). So it caps everything:

| What              | Cap    | Beyond it               |
|-------------------+--------+-------------------------|
| parameters        | 32     | extra ones are dropped  |
| one parameter     | 65535  | it stays at 65535       |
| OSC data          | 4 KiB  | the rest is dropped     |

* Sequences that cross reads

A read can end in the middle of a sequence: one read ends with =\e[01;3= and
the next starts with =1mred=. The parser is a value (a struct), and
everything it was doing, including half-built parameters, carries over to
the next =feed/2= call.

A property test feeds random combinations of sequences, cut at random
points, and checks the commands are always the same as when fed whole.
Another feeds random bytes and checks it never crashes.

* Fast path for text

Most bytes are plain text, so =ground= counts how many printable bytes come
in a row and emits them as a single ={:print, run}= (a sub-binary, no
copying), instead of one command per byte. OSC data is collected in runs
the same way.

* Questions

1. How does the parser know where a CSI sequence ends?
2. What's the difference between =38;2;255;0;0= and =38:2::255:0:0=?
3. Why execute a CR that arrives in the middle of a CSI sequence?
4. Why cap the number of parameters?
5. Why are parsing and meaning in different modules?

** Answers
:PROPERTIES:
:VISIBILITY: folded
:END:

1. At its final byte, anything from =0x40= to =0x7E=.
2. The first is five separate parameters that SGR has to group by
   convention. The second is one parameter with sub-parameters, so it's
   unambiguous (and leaves room for a color-space id between the colons).
3. Real terminals do, and programs (rarely) rely on it.
4. Bytes come from programs we don't control. Without a cap, a hostile
   =ESC [ 1;1;1;...= could make the parser build a huge list.
5. The parser can be finished and tested once; new features only touch
   =Terminal=, and a syntax bug can't hide in the code that moves cursors.
