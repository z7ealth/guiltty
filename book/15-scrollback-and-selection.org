#+TITLE: Scrollback, search and the clipboard
#+STARTUP: overview

* The scrollback

When a line feed at the bottom of the screen scrolls everything up, the
top row used to vanish. Now, on the main screen, it goes into the
scrollback. (Not on the alternate screen: vim's redraws aren't history.
Not when a scroll region is set: that's a program scrolling part of its
own screen.)

** Numbering

Every row that ever scrolled off gets a number, from 0 up. The screen's
rows continue the count:

#+begin_example
   row number
        0   line 1      <- scrollback_first (oldest kept)
        1   line 2
      ...
     9999   line 10000
                        <- history = 10000 (rows that ever scrolled off)
    10000   screen row 0
    10001   screen row 1
      ...
#+end_example

The numbers never change as more output arrives, which is the point: a
selection, a search match, or the view while you're scrolled back all hold
row numbers, so they stay on their text while the shell keeps printing.
Past =scrollback_max= rows (10,000 by default, =scrollback:= in the config),
the oldest go and =scrollback_first= moves up.

** Storage: blocks of 256 rows

A naive version kept a map from row number to row. It halved guiltty's
speed on a flood of short lines: one map update and one memory allocation
per line. The scrollback now has two parts:

#+begin_example
  recent:  [row 9999, row 9998, ..., row 9984]     a list, newest first
                                                   (a row costs one prepend)
  blocks:  %{38 => {starts, rows}, 37 => ..., 0 => ...}
             block b holds rows b*256 .. b*256+255:
             rows   = one binary, the 256 rows end to end, each without
                      its trailing blank cells
             starts = a tuple of where each row begins in it
#+end_example

Every 256 rows, =recent= is sealed into a block: one binary, one
allocation. Finding row =n= is =div(n, 256)= for the block, then
=binary_part= at =elem(starts, rem(n, 256))=: O(1). Most rows are short, so
trimming their blank cells saves a lot: 10,000 rows of =seq= output take
0.56 MB instead of 11.2 MB at full width (80 cells of 14 bytes).

Measured (feeding the parser and grid directly, 400,000 short lines):
6.6 MB/s with scrollback; MVP 4's grid did 7.0 MB/s without any.

Code: =save_lines/2=, =seal/1= and =line/2= in [[file:../lib/guiltty/grid.ex][Guiltty.Grid]].

* The view

What the window shows is the Screen's business, not the grid's: the grid
is the terminal's state, and scrolling back doesn't change it. The Screen
keeps =scroll= (how many rows back), =selection= and =search=, and
[[file:../lib/guiltty/view.ex][Guiltty.View]] builds the rows to send:

#+begin_example
   scroll = 0                    scroll = 2
   +----------------+            +----------------+
   | screen row 0   |            | scrollback -2  |
   | screen row 1   |            | scrollback -1  |
   | screen row 2   |            | screen row 0   |
   +----------------+            +----------------+
   cursor shown                  cursor (row 2) scrolled out: hidden
#+end_example

Marks go on copies of the rows, never into the grid: the selection flips
=inverse=, search matches get the =match= bit (0x400) and the current one
=current_match= too (0x800). The renderer colors those yellow.

While the view is decorated (scrolled, a selection, a search), each update
sends every visible row; when it stops being decorated, one more full
update puts the plain rows back.

** Staying on the same text

You scroll back to read something and the build you started keeps
printing. Each new row entering the scrollback would move the text up
under you, so =keep_view/2= adds the number of new rows to =scroll=: the
view stays on the same row numbers. Typing anything brings it back to
the bottom.

* Scrolling

| Input                   | Scrolls                                         |
|-------------------------+-------------------------------------------------|
| mouse wheel             | 3 rows (unless the program wants the mouse)     |
| Shift+PgUp / Shift+PgDn | a page (rows - 1)                               |
| Shift+Home / Shift+End  | to the top / back to the live screen            |
| typing                  | back to the live screen                         |
| Ctrl+Shift+K            | nowhere: drops the scrollback (=CSI 3 J=, ch. 24) |

On the alternate screen there's no scrollback, so the wheel sends arrow
keys instead (xterm calls it =alternateScroll=): =less=, =man= and =git log=
scroll with the wheel.

* Search

Ctrl+Shift+F starts a search; what you type goes into the query, shown at
the right of the tab bar (a STATUS message), not to the program. Each
keystroke searches again from the newest output; Enter goes to the next
older match, Shift+Enter to the next newer one, Escape ends it.

[[file:../lib/guiltty/search.ex][Guiltty.Search]] works row by row and cell by cell:

1. Turn the row into text and check =String.contains?=: most rows don't
   match, and that test is cheap.
2. Only for rows that do: compare the query's graphemes with the cells'
   text, so a match is in columns (=日本語 ok=: "ok" is at columns 7-8,
   though it's at byte 10).

It's case-insensitive unless the query has a capital letter (smart case,
like vim and less). Searching all 10,000 rows for something that isn't
there takes about 45 ms.

* Selection

Who owns the selection was a design decision: Elixir. The renderer only
has the visible cells; Elixir has the scrollback and knows clusters and
wide characters. So the renderer just reports mouse events, and the
Window decides:

#+begin_example
  mouse event
     |
     +-- the program asked for the mouse (1000/1002/1003) and no Shift?
     |      yes -> encode it for the program (chapter 7)
     |
     +-- no -> guiltty's own:
            left press    Screen.select {:start, pos, clicks}
            left drag     Screen.select {:extend, pos}
            left release  Screen.select :finish  -> text -> PRIMARY
            middle press  ask the renderer to paste PRIMARY
            wheel         scroll (or arrow keys on the alternate screen)
#+end_example

Shift held forces a selection even in vim or htop, as in xterm.

A selection is an anchor and a head (row numbers and columns) and a mode
from the click count SDL reports: one click selects by character, a
double click by word, a triple click whole rows. A press and release on
the same cell is just a click: it clears the selection. Selected text never
has half a wide character, and rows are joined as the next section says
([[file:../lib/guiltty/selection.ex::def text][Guiltty.Selection.text/2]]).

** Lines that only wrapped

A row of the grid isn't a line of text. A compiler error 150 characters
long, on an 80-column screen, takes two rows, but the program printed one
line. The grid knows the difference: when text runs past the last column,
the last cell of the row gets a =wrapped= bit (the same bit reflow uses,
see chapter 9).

So copying joins rows the way they were printed:

#+begin_example
  printed: "error: expected ';' after expression at src/main.c:42:17\n" on 30 columns

  row 0  |error: expected ';' after expr|>    wrapped (bit on the last cell)
  row 1  |ession at src/main.c:42:17    |     ended with Enter

  copied before v0.24:  "error: expected ';' after expr\nession at src/main.c:42:17"
  copied now:           "error: expected ';' after expression at src/main.c:42:17"
#+end_example

A wrapped row keeps its trailing spaces: the space in "hello wor ld",
when it lands exactly on the last column, is text, not padding. Other
rows lose them, since there a space is just an empty cell. The wrap only
counts when the selection reaches the end of the row: stop halfway
along a wrapped row and the text after it starts a new line.

** Select all

Ctrl+Shift+A (=select_all=) is the keyboard's way to the same thing:
=Screen.select(id, :all)= builds a selection from the oldest row of
scrollback to the last row with text, by character, as if you had dragged
over all of it ([[file:../lib/guiltty/selection.ex::def all][Selection.all/1]]).
The end isn't the bottom of the screen: below a shell's prompt there are
usually empty rows, and copying them would put a run of blank lines at the
end of what you paste. So it walks up from the bottom to the first row
that isn't blank, and never above the cursor's row. On the alternate
screen there's no scrollback to take (vim's rows aren't your shell's
history), so it starts at the screen's top.

#+begin_example
  "line 1\r\n ... line 5\r\n$ " on a 10x8 screen (the test in scrollback_test.exs)

  row 0   line 1     <- scrollback_first = history = 0   anchor {0, 0}
  row 1   line 2
  ...
  row 4   line 5
  row 5   $ _        <- the cursor                        head   {5, 9}
  row 6              (blank: left out)
  row 7              (blank: left out)

  Selection.text -> "line 1\nline 2\nline 3\nline 4\nline 5\n$"
#+end_example

With scrollback, only the top moves: the anchor is =scrollback_first=,
the oldest row still kept, whose number keeps counting up as old rows
are dropped.

The Window then treats the text as the end of a drag: =copy_selected/2=
sends it to PRIMARY (and to CLIPBOARD too with =copy_on_select:
:clipboard=), so the mouse and the key share one rule.

** The last command's output

Ctrl+Shift+G (=copy_output=) copies what the last command printed,
and only that: not the prompt, and not the command line. A terminal
can't tell any of that from the text alone, because to the grid a
prompt is characters like any others. The shell has to say where
things are, and shells that support it use *shell integration* marks,
FinalTerm's OSC 133:

#+begin_example
  ESC ] 133 ; A BEL    a prompt starts here           (precmd, before PS1)
  ESC ] 133 ; B BEL    you type the command here      (end of PS1; unused)
  ESC ] 133 ; C BEL    Enter: the output starts here   (preexec)
  ESC ] 133 ; D ; 0 BEL  the command ended, status 0   (precmd, next time)
#+end_example

guiltty used A since v0.20 to jump between prompts (Ctrl+Shift+Z / X).
Now C and D matter too. On C, the grid remembers the cursor's row number
as where output starts. On D, it remembers where the output ended: the
row after the last one with output. That's the cursor's row if the
cursor is at column 0 (the output ended with a newline), or the row after
it if not ([[file:../lib/guiltty/grid.ex::def mark_output_start][Grid.mark_output_start/1]]). A shell that never sends D
still sends A for its next prompt, so A ends any output that's still open.

Here is a real grid, two commands on a 20x8 screen, from iex:

#+begin_example
  bytes: A "$ ls\r\n" C "a.txt\r\nb.txt\r\n" D  A "$ echo hi\r\n" C "hi\r\n" D  A "$ "

  row 0   $ ls        <- A
  row 1   a.txt       <- C         output_marks: [{4, 5}, {1, 3}]
  row 2   b.txt                    (newest first: {first row, row after the last})
  row 3   $ echo hi   <- D, A      prompt_marks: [5, 3, 0]
  row 4   hi          <- C
  row 5   $ _         <- D, A      Grid.last_output -> {4, 4}

  Ctrl+Shift+G copies "hi"
#+end_example

The marks are row *numbers*, the same ones the scrollback counts with
(see "Numbering" above), so output longer than the screen is still found
in the scrollback. They follow their rows through a reflow, as the prompt
marks and links do. If the start of the output has scrolled out of the
scrollback, you get what's left; if all of it has, there's nothing to copy.
A command that's still running counts too: you get what it has printed so
far, down to the cursor. On the alternate screen (vim, htop) marks are
ignored, since those rows aren't your shell's history.

The Window asks the Screen to select those rows, as if you had dragged
over them, so you see what was copied, and puts the text on the
CLIPBOARD (like Ctrl+Shift+C, not PRIMARY: you asked for a copy). The
status says what happened: copied, "the last command printed nothing",
or that the shell doesn't mark its commands.

*** Shells that mark only prompts

Some setups send A and nothing else. Then guiltty can still guess: the
output of the last command is everything between the last two prompts,
less the command line. The command line starts on the prompt's row and
goes on over any rows it wrapped into, so a long command is left out
whole ([[file:../lib/guiltty/grid.ex::defp command_end][command_end/2]]):

#+begin_example
  row 0   $ ls        <- A (the older prompt)
  row 1   a           <- the guess starts on the row after the command line
  row 2   b
  row 3   $ _         <- A (the newest)        Grid.last_output -> {:guess, {1, 2}}
#+end_example

It's a guess because a prompt of two lines (a path above, =$= below)
makes it start one row early. So the status says "copied a guess", and
points to the book for the real marks.

*** Turning the marks on

Most shells don't send them by default. Some ways to get them:

- *zsh with powerlevel10k*: =typeset -g POWERLEVEL9K_TERM_SHELL_INTEGRATION=true=
  in =~/.p10k.zsh=.
- *fish* 4 sends them by itself.
- *zsh*, by hand, in =~/.zshrc=:

#+begin_src sh
  _mark_prompt() { print -n '\e]133;D;'$?'\a\e]133;A\a' }
  _mark_output() { print -n '\e]133;C\a' }
  precmd_functions+=(_mark_prompt)
  preexec_functions+=(_mark_output)
#+end_src

- *bash*: =PS0= runs when you press Enter, and =PROMPT_COMMAND= before each prompt:

#+begin_src sh
  PS0='\[\e]133;C\a\]'
  PROMPT_COMMAND='printf "\e]133;D;%s\a\e]133;A\a" $?'
#+end_src

** When the text under it changes

Because a selection holds row numbers, it follows its text as output
scrolls it up into the scrollback. But if the text itself changes (you
run =clear=, a program redraws), the rows still exist and the selection
would highlight whatever is there now: a block of inverted color over a
blank screen. So when the mouse lets go, the Screen remembers the text it
selected, and after every change it compares (=drop_stale_selection/1=):
same text, the selection stays; different, it goes, and every row is sent
again without the highlight. Comparing the text, not "did those rows
change", is what lets a selection survive scrolling, which changes every
row on screen but not the text it points at.

* Links from the keyboard

Ctrl+click opens a link (chapter 20), but that needs the mouse. Ctrl+Shift+J
(=hints=) labels every link on screen with letters, as Vimium does in a
browser and Kitty and Alacritty do in a terminal; type a label, and that link
opens:

#+begin_example
  before                                   after Ctrl+Shift+J
  $ mix phx.server                         $ mix phx.server
  Access at http://localhost:4000          Access at [a]tp://localhost:4000
  docs: https://hexdocs.pm/phoenix         docs: [s]tps://hexdocs.pm/phoenix

  typing s opens https://hexdocs.pm/phoenix; Escape, or a letter no label
  starts with, ends it
#+end_example

The pieces are ones guiltty already had:

- *Finding the links.* =Url.visible/3= runs the same pattern as Ctrl+click
  ([[file:../lib/guiltty/url.ex::def visible][Guiltty.Url]]) over every
  logical line in view, so a URL that wrapped is one link, with a span on
  each row it takes.
- *Labels.* The home row first: =a s d f g h j k l=, then the rest of the
  alphabet. With more than 26 links every label is two letters. No label
  is the start of another, so a label opens the moment it's complete, with
  no waiting to see whether more letters follow.
- *Drawing them.* Nothing new in the renderer. The Screen already sends
  decorated rows for search matches and the selection (=View.rows/5=);
  =View.hints/3= adds an underline under each link and writes its label
  over the link's first cells in reverse video. As you type, labels that
  no longer match go away, and the letters you've typed drop off the rest.
- *Opening.* The same =open_link/2= as Ctrl+click: only =http=, =https=,
  =mailto= and =file= open, and the status shows where the link goes.

Only links in plain text get labels for now: OSC 8 links (a program
saying "this text links there") are for Ctrl+click.

** The hand over a link

With Ctrl held, moving over a link underlines it, and the pointer turns
into a hand, as it does in a browser. The Screen answers =hover/3= with
whether there's a link under the pointer, and the Window tells the
renderer only when the shape changes: POINTER 1 for the hand, POINTER 0
for the default (protocol version 15). The renderer makes the hand with
=SDL_CreateSystemCursor(SDL_SYSTEM_CURSOR_POINTER)= the first time it's
needed and keeps it; if the cursor theme has no hand, the pointer just
stays as it is.

* Two clipboards (on X11)

X11 has several *selections*; two matter:

- *PRIMARY*: whatever you last selected. Middle-click pastes it. No copy
  command: selecting is copying.
- *CLIPBOARD*: what an explicit "copy" put there. Ctrl+V pastes it in
  most programs; in a terminal, Ctrl+Shift+V (Ctrl+V is a control
  character for the shell).

Neither holds data. A selection has an *owner*, the program that claimed
it; pasting asks the owner to send the text over. So if the owner
quits, the clipboard is empty. (Clipboard managers exist to work around
that.) Wayland keeps the same idea, with the data-device protocol for
CLIPBOARD and the primary-selection protocol for PRIMARY. SDL3 hides both:
=SDL_SetClipboardText=, =SDL_SetPrimarySelectionText= and their getters.

The renderer owns guiltty's selections, since it's the X11 client, so
Elixir tells it what to own:

| Action                  | Messages                                                |
|-------------------------+---------------------------------------------------------|
| select with the mouse   | Elixir -> renderer CLIPBOARD (target 1, primary)        |
| Ctrl+Shift+A            | the same, for everything (select all)                   |
| Ctrl+Shift+C            | Elixir -> renderer CLIPBOARD (target 0, clipboard)      |
| Ctrl+Shift+V            | renderer reads CLIPBOARD, sends PASTE                   |
| middle click            | Elixir -> renderer PASTE_PRIMARY; renderer sends PASTE  |

A paste goes through =Keymap.paste/2= as before: line endings become CR,
and in bracketed paste mode the text is wrapped (and cleaned of fake
end markers).

* Right click

With text selected, a right click does what you'd do by hand next: it puts the text
on the clipboard, pastes it at the prompt of the pane under the pointer, and clears
the selection. The text can come from any pane of the tab, which makes it a quick way
to take a path from one shell's output to another shell's prompt. It's a paste like
any other: bracketed if the program asked (chapter 7), and it goes to the whole
broadcast group if the focused pane is in one. With nothing selected, it does nothing.

Like every local mouse action, it's for when the program didn't ask for the mouse;
in one that did (=vim=, =htop=), hold Shift.

* Questions

1. Why give scrollback rows numbers that never change?
2. Why doesn't the alternate screen add to the scrollback?
3. You're scrolled back 100 rows and 5 new rows scroll off. What's
   =scroll= now, and why?
4. What's the difference between PRIMARY and CLIPBOARD?
5. Why does Elixir own the selection, not the renderer?
6. Why does sealing 256 rows at a time make guiltty faster?
7. Why does guiltty compare the selected text instead of checking whether
   the selected rows changed?
8. Why can't guiltty find the last command's output by itself, without
   OSC 133? And why does an A mark end the output, as well as D?
9. Why does a wrapped row keep its trailing spaces when copied, when
   other rows lose them?
10. Why are hint labels either all one letter or all two, never mixed?

** Answers
:PROPERTIES:
:VISIBILITY: folded
:END:

1. So anything that points into the text (a selection, a match, the
   view) stays on the same text while new output arrives.
2. Full-screen programs redraw the alternate screen constantly; that's not
   history, and saving it would bury the real output.
3. 105: the view moves back by the 5 new rows, so it keeps showing the
   same text.
4. PRIMARY is the last selection (middle-click pastes it); CLIPBOARD is
   what an explicit copy put there (Ctrl+Shift+V pastes it).
5. Only Elixir has the scrollback and the cluster table; the renderer
   only mirrors visible cells.
6. A list prepend per row is nearly free; the map update and the memory
   allocation happen once per 256 rows instead of once per row.
7. Scrolling changes every row on the screen but not the text a selection
   points at (its row numbers move with it). Only a change to that text
   should drop the selection.
8. To the grid, a prompt is just characters: =$ =, a powerline arrow, two
   lines with a clock. Only the shell knows where its prompt ends and a
   program's output starts, so it has to say so. A ends output too because
   some shells and setups send no D, and a new prompt means the command
   before it is certainly done.
9. On a wrapped row, the text went on past the edge: a space in the last
   column is part of what was printed ("wor ld"). On a row that ended
   with Enter, cells after the text are just empty cells.
10. So no label is the start of another. With "a" and "as" both labels,
    typing =a= couldn't open anything until guiltty knew whether =s= was
    coming.
