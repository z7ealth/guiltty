#+TITLE: Performance: measure, then fix what the numbers say
#+STARTUP: overview

* The rule

guiltty is an Elixir program with a renderer in C. It won't be as fast
as Ghostty or Alacritty, which are single native programs, and v0.14.0
didn't try to change what guiltty is. It looked for what was slow for no
good reason, and every change came with a number before and after.

* Measuring

Three tools, all in [[file:../bench/][bench/]]:

| Tool                         | Measures                                         | Run                    |
|------------------------------+--------------------------------------------------+------------------------|
| =bench/throughput.exs=       | the parser and the grid alone, on made-up streams | =make bench=           |
| =bench/end_to_end.exs=       | a real shell =cat=-ing a file into a real window, offscreen | =make bench=  |
| =bench/time_to_window.sh=    | from running a terminal to its window on screen  | with =hyperfine=       |

The streams are generated by the scripts, so the numbers don't depend on
what's on the machine:

- *scrolling*: short lines, so the screen scrolls on almost every one
  (=seq=, logs);
- *colors*: long lines with a color change every word (=ls --color=);
- *unicode*: wide characters, emoji, combining marks;
- *full screen*: cursor moves and a row each, like =htop= redrawing.

Time to window needs a window manager and must run from another terminal
(guiltty can't time its own start while it runs). How to run it against
alacritty and ghostty is in the script's header; the first result, one
=hyperfine= run of each on the development machine, was alacritty
130 ms, ghostty 260 ms, guiltty 1,230 ms, more than half of it the
launcher (see "Not done", below). Only start-up was compared, not
throughput.

To find /where/ the time goes, OTP's profiler counts the time in every
function:

#+begin_src elixir
Mix.ensure_application!(:tools)
:tprof.profile(fun, %{type: :call_time, report: {:total, {:measurement, :descending}}})
#+end_src

* The grid: scrolling 5.5x faster

The first profile of the scrolling stream (real output, trimmed):

#+begin_example
  FUNCTION                              CALLS  TIME (us)  [    %]
  maps:from_keys/2                      68254     228364  [19.83]   <- all_dirty
  binary:copy/2                         68520      89160  [ 7.74]   <- blank_line
  binary:longest_common_suffix/1        68096      85110  [ 7.39]   <- trim_line
  'Elixir.Guiltty.Grid':replace_cells/4 68357      40765  [ 3.54]
  ...
#+end_example

None of those is the grid's design. Four changes, each measured:

| Change                                                   | scrolling |
|----------------------------------------------------------+-----------|
| before                                                   | 0.8 MB/s  |
| "every row changed" is =:all=, not a set of all rows      | 1.5 MB/s  |
| lines of plain text laid down together, scrolled once    | 2.5 MB/s  |
| scrollback rows trimmed by binary search                 | 2.8 MB/s  |
| rows that scroll straight off are made short to begin with | 4.4 MB/s  |

** Dirty rows as :all

Each scroll moves every row, so the grid marked every row dirty by
building a fresh set of all row numbers: =MapSet.new(0..39)=, forty
inserts, on every line feed. Now it's the atom =:all=, turned into rows
only when the Screen takes them (=take_dirty/1=). The blank row a scroll
brings in is made once per width and background and reused: binaries are
immutable, so every blank row can be the same one.

** Lines in a batch

=seq 1 100000= reaches the grid as thousands of the same three commands:

#+begin_example
  {:print, "12"}, :cr, :lf, {:print, "13"}, :cr, :lf, ...
#+end_example

One by one, each line writes its text into the bottom row, shifts all
forty rows up, saves one row to the scrollback and marks everything
dirty. =Terminal.apply/2= now collects those triples and hands them to
=Grid.print_lines/2= together. When the result is sure to be the same,
it builds the rows directly and scrolls once, by all of them:

#+begin_example
  before                   N lines            after
  +--------------+                            +--------------+
  | row 0        | ----> scrollback           | (old rows    |
  | ...          |       (first N rows of     |  still on    |
  | row 38       |        old + new)          |  screen)     |
  | (blank)  <-- cursor    + "12" "13" ... -> | new rows     |
  +--------------+                            | (blank) <-- cursor
                                              +--------------+
#+end_example

"Sure to be the same" means: the cursor at the start of a blank bottom
row, the scroll region the whole screen, no insert mode, no line-drawing
set, plain ASCII that fits on a row. When the grid isn't ready (the line
before was cut by the end of a read, so the cursor is mid-row), one line
goes the usual way and the rest try again. The last line always goes the
usual way, so whatever that remembers (the last character, for REP) is
as before.

** Scrollback rows, short from the start

Rows are kept in the scrollback without their trailing blank cells. That
trimming used =binary:longest_common_suffix/1= and cost 1.25 µs a row;
now a binary search finds where the content ends, each step one binary
comparison against a row of blank cells made once (=@blanks=). Better
still, in a big batch most new rows scroll straight off the screen, and
the batch knows their text, so it saves them short to begin with: a full
120-cell row is only made for the rows that stay on screen.

** Faster, never different

A fast path that gives a different screen is a bug, however fast.
[[file:../test/guiltty/batch_lines_test.exs][batch_lines_test.exs]] checks the grid is /exactly/ the same both ways:
the commands applied together (fast) and one at a time (a list of one is
never a batch). Random lines: empty, trailing spaces, too long for the
row, not ASCII, colored, cut mid-row, with a scroll region, the
alternate screen, insert mode, the line-drawing set. The first version
failed it: the fast path kept the newest scrollback rows trimmed, the
slow path full width until a block of 256 was sealed. No one would have
seen it, but the test said "different", so now every row is trimmed when
it's saved, and both paths agree byte for byte.

* Text into cells: a second NIF

** A 1.1 GB log

=cat= of a 1.1 GB log took 11 s in one terminal, 17 s in another and
4 min 36 s in guiltty: 4 MB/s. Every line had a colored level, accents,
✓, 漢字 and 🚀. =cat= used 3% of a CPU, so it wasn't stuck: guiltty was
reading slowly, and the PTY's backpressure held =cat= back. A profile of
8 MB of that file, parser and grid alone:

#+begin_example
  parser only            57 MB/s
  parser + grid         3.3 MB/s

  FUNCTION                              CALLS  TIME (us)  [    %]
  'Elixir.String':do_graphemes/1      1221674     167752  [14.96]
  unicode_util:gc/1                   1221674     129629  [11.56]
  'Elixir.Guiltty.Grid':'-intern_units/2-fun-1-'/2
                                       598819      84981  [ 7.58]
  'Elixir.Enum':'-map_reduce/3-...'/3  606831      79004  [ 7.04]
  'Elixir.Guiltty.Grid':intern/2       598819      54246  [ 4.84]
  'Elixir.Guiltty.Unicode':width/1     632218      46493  [ 4.15]
#+end_example

The grid had an ASCII fast path, but only for text that is ASCII from
end to end. One =ü= sent the whole line down the slow road: split into
grapheme clusters, each one interned and measured, one at a time.

** The trick: most text can't join anything

UAX #29 decides where clusters end by each codepoint's /grapheme break
property/. Nearly everything printed has the property "Other": letters,
digits, CJK, arrows, most emoji. And between two "Other" codepoints the
answer is always "break" (rule GB999). Only the rest (Extend, ZWJ,
SpacingMark, Prepend, regional indicators, Hangul jamo, controls) ever
joins.

So C doesn't segment anything. [[file:../c_src/text_nif.c::segments][segments/4]] makes a cell of each
codepoint that is "Other" /and/ whose neighbours are both "Other", and
returns the rest as text, which Elixir segments as before:

#+begin_example
  iex> Guiltty.TextNif.segments("abc🚀🏽def", 0, 0, 0)
  [{<<0, 0, 0, 97, ...>>, 3}, "🚀🏽d", {<<0, 0, 0, 101, ...>>, 2}]

   a  b  c  🚀 🏽 d  e  f
   O  O  O  O  X  O  O  O        O = "Other", X = Extend (the skin tone)
  [cells  ][text   ][cells]
            ^        ^
            🚀 and d touch an X: they go with it
#+end_example

The text pieces are cut between two "Other" codepoints, where a break is
certain, so segmenting each piece alone gives the same clusters as
segmenting the whole line. (Rules that look back, like a ZWJ sequence or
an Indic conjunct, need a non-"Other" codepoint right before the joining
point, and that one is always in the text piece too.)

#+begin_example
  Grid.print(text)
    ASCII? ---------------------------------> put_text (one byte, one cell)
    joins the last cluster printed? --------> segment again in Elixir
    autowrap off? --------------------------> Elixir
    otherwise: TextNif.segments(text, pen)
       {cells, cols} --> put_cells: as many columns as fit per row;
                         a wide character never splits across rows
       "text"        --> String.graphemes -> put_graphemes (as before)
#+end_example

** The table

The NIF looks each codepoint up in [[file:../c_src/text_table.h][c_src/text_table.h]]: 494 ranges in
three classes, narrow, wide and complex. The generator,
[[file:../c_src/tools/gen_text_table.exs][gen_text_table.exs]] (=make text-table=), takes the widths from
=Guiltty.Unicode.WidthTable=, the table Elixir uses, so the two can't
disagree on a width. Printable ASCII skips the search.

The break property comes from Unicode's =GraphemeBreakProperty.txt=, but
which version? Each OTP segments with its own: OTP 26 has Unicode 15.0,
OTP 29 has 17.0. With 17.0 alone, the every-codepoint test passed on
OTP 29 and failed on OTP 26 on one codepoint, U+11A3A (𑨺, Zanabazar
Square), "Prepend" in 15.0 and "Other" since 15.1. So the table takes
all four versions guiltty's OTPs use, and a codepoint is complex if it
is in /any/ of them. Calling something complex is always safe: it only
means the running OTP decides.

#+begin_example
  version       15.0     15.1     16.0     17.0     table
  U+11A3A       Prepend  Other    Other    Other    complex
  U+0301 ◌́      Extend   Extend   Extend   Extend   complex
  U+0061 a      Other    Other    Other    Other    narrow
#+end_example

Its first output called 가 wide instead of complex: =Regex.run= leaves
out an optional group that didn't match, so every single-codepoint line
of the Unicode file was skipped. A spot check caught it before the tests
did.

** Faster, never different (again)

Two tests, the same idea as the batch path's:

- [[file:../test/guiltty/text_nif_test.exs][text_nif_test.exs]] feeds the NIF /every codepoint there is/, each
  between two letters, plus random mixes of the pieces that join (ZWJ,
  flags, jamo, a Devanagari conjunct), and checks the clusters and widths
  are exactly =String.graphemes/1= and =Unicode.width/1='s, on whatever
  OTP runs the suite. Run on OTP 26, it's what found U+11A3A.
- [[file:../test/guiltty/print_nif_test.exs][print_nif_test.exs]] prints random text through the NIF and through
  Elixir alone (=Grid.print_in_elixir/2=) into narrow grids, at random
  columns, in insert mode or not, in several prints, and checks the
  grids are identical. With a planted bug (the last column not blanked
  when a wide character wraps), it fails.

** Inside the scheduler

A NIF holds its scheduler until it returns, and should return within
about 1 ms. The input is at most one PTY read, 64 KB, which takes 0.41 ms
here; the NIF tells the scheduler how much of its timeslice it used
(=enif_consume_timeslice=). It has no state and makes no syscalls, so
the reasons the renderer is a separate process don't apply: it can't
block, and it's tested against Elixir on every codepoint.

** What it bought

The NIF alone: 108 MB/s, against 23 MB/s for the Elixir path. The whole
pipeline on the log: 3.8 to 7.6 MB/s (see Results). Twice as fast, not
five times, because the grid was only most of the time. Now nothing
stands out; the biggest item is the parser walking text byte by byte
(14%), then a long tail of small Elixir costs.

* Small things, and a profiler that exaggerates

Next came the items the profiles named, each small:

- the parser's text runs found by the NIF (=text_run/1=) instead of one
  Elixir step per byte, with control bytes kept in Elixir ([[file:03-parser.org][chapter 3]]);
- =ascii?= done by the NIF instead of =:binary.match= with a pattern
  fetched from =persistent_term= on every print;
- ASCII text turned into cells by the NIF (=ascii_cells/4=), in
  =write_cells= and the batch path, instead of a comprehension per byte;
- a cell's attrs read by a binary match instead of =binary_part= plus
  =:binary.decode_unsigned/1=. Every write checks the cells at its edges
  for half a wide character, so this runs several times per write.

The profiles had made them look big: =attrs_at= and =decode_unsigned=
were 16% of the colored stream, =text_run= 9% of the scrolling one. Best
of 15 runs, old and new code in turn, twice:

| Stream (=parser + grid=) | before    | after     |       |
|--------------------------+-----------+-----------+-------|
| full screen              | 21.5 MB/s | 33 MB/s   | +55%  |
| unicode                  | 5.05 MB/s | 5.7 MB/s  | +13%  |
| scrolling                | 4.0 MB/s  | 4.45 MB/s | +10%  |
| log                      | 7.5 MB/s  | 7.8 MB/s  | noise |
| colors                   | 2.25 MB/s | 2.2 MB/s  | none  |

The colored stream, where =attrs_at= "was" 16%, didn't move. =tprof='s
=call_time= mode times every call, and timing a call costs about as
much as a tiny function does: functions called millions of times look
several times bigger than they are. It ranks well; its percentages of
small functions are not to be believed. The measured runs are what
count, and they need repeating: on a desktop that's doing other things,
the same code gave 3.9 and 4.7 MB/s for scrolling a minute apart.

What does the colored stream spend its time on, then? Every short
colored word is its own print, and every print rebuilds its whole row
binary (=replace_cells=: the cells before, the new ones, the cells
after). A 120-column row is 1,680 bytes, rebuilt 24 times per line.
That's the batch path's job (DEVLOG "Later": colored lines).

* The renderer: only the rows that changed

The OpenGL backend already kept last frame's cells on the GPU and
uploaded only the changed rows. The Vulkan backend copied every cell,
every frame, because it has two frames in flight, each with its own copy
of the cells: a row that changes must reach /both/ copies, one frame
apart.

#+begin_example
  frame   rows changed   slot   stale before   copied   stale after
  -----   ------------   ----   ------------   ------   -----------
  1       5              A      A:5  B:5        A:5     A:-  B:5
  2       9              B      A:9  B:5..9     B:5..9  A:9  B:-
  3       (none)         A      A:9  B:-        A:9     A:-  B:-
#+end_example

Each slot remembers the range of rows it's behind on; every frame adds
its changed rows to both; the slot being drawn copies its range and
clears it. Two traps: the rows must be noted /before/ =draw_frame= can
return early (a swapchain being rebuilt), because the core forgets them
once the call returns; and a new grid size or a new buffer means a full
copy.

How much does it save? At 120 x 40 a full copy is 57 KB, a few
microseconds; it matters for big windows with small changes (typing in a
300 x 80 window: 3.6 KB a frame instead of 288 KB). The point was as
much to have Vulkan and OpenGL work the same way.

** Testing it

A replay used to draw once after reading every message, so it never
tested this. Now it draws after each ROWS message, the way a live window
does (Elixir sends the next update only after the frame report). The
test replays thirty small updates (writes, scrolls, cleared rows), each
sending only the rows that changed, and checks the last frame is exactly
the one a single whole update gives. With a planted bug (only the
current slot marked stale), it fails.

* The node's boot

Each milestone of a cold start of a release, from the start command (on
Xvfb with software OpenGL, so the last step is slower than on a GPU):

#+begin_example
  config loaded     ~510 ms   the VM has booted and guiltty has started
  shell started       +4 ms
  renderer hello      +3 ms
  first frame       +90-180 ms
#+end_example

guiltty's own code takes milliseconds; almost all of it is the VM. A bare
VM from the release (only kernel and stdlib, halting at once) takes
0.35-0.39 s: the BEAM's JIT compiles every module it loads to machine
code. So the cheap fix was to load fewer modules at boot. A Mix release
starts in /embedded/ mode, loading every module of every application
first; /interactive/ mode loads each the first time it's used:

| Mode                    | config loaded | first frame |
|-------------------------+---------------+-------------|
| embedded (before)       | ~545 ms       | ~650 ms     |
| interactive (now)       | ~435 ms       | ~545 ms     |
| no distribution (test)  | ~540 ms       | ~635 ms     |

Distribution costs nothing measurable. Interactive mode's price is a few
milliseconds the first time something is used (the cheatsheet, say), as
its module loads. It's set in [[file:../rel/env.sh.eex][rel/env.sh.eex]] (=RELEASE_MODE=).

* Not done (DEVLOG "Later")

- *The launcher*: ~0.7 s of a cold start, and all of a warm one, was
  =guiltty= booting a second VM to ask the first "are you running?".
  Left out of v0.14.0 on purpose, and done properly in v0.15.0: a small C
  client and a socket server (chapter 23).
- *Colored lines*: they have color codes between the text and the line
  feed, so they don't take the batch path. Batching them means following
  SGR inside the batch.
- *Colored lines, again*: each colored word is a print that rebuilds
  its whole row. Collecting a line's prints and rebuilding the row once
  is the next real gain for =ls --color= and compilers.
- *Parser and grid in C*: the only way to Ghostty's speed, but then the
  grid stops being Elixir terms. Not planned.

* Questions

1. Why measure before changing anything, when the profile "obviously"
   pointed at =maps:from_keys/2=?
2. Why does the batch path send the /last/ line the usual way?
3. The fast path was correct on screen but failed the equivalence test.
   What differed, and why fix something no one would see?
4. Why must a changed row be marked stale in both Vulkan slots?
5. Why is a bare VM boot the floor for guiltty's start, and what did
   interactive mode change about it?
6. The text NIF never segments anything. How can it still return the
   same clusters as =String.graphemes/1=?
7. In =abc🚀🏽def=, why does =d= come back as text, though it's an
   ordinary letter?
8. Why is a NIF fine for this, when the renderer had to be a separate
   process?
9. Moving =text_run= into C first made the parser slower. Why, and what
   fixed it?
10. =attrs_at= was 16% of the colored stream's profile, and making it
    cheaper gained nothing there. How can both be true?

** Answers
:PROPERTIES:
:VISIBILITY: folded
:END:

1. A profile shows where time goes, not what a change will gain. Fixing
   =all_dirty= took scrolling from 0.8 to 1.5 MB/s, far from the 5x
   needed; only measuring after each change showed what came next.
2. So that whatever the usual way remembers (the last character printed,
   which REP repeats and a combining mark may join) comes out exactly as
   it always did, without the fast path having to copy that logic.
3. The newest scrollback rows (not yet sealed into a block) were kept
   trimmed by the fast path and full width by the slow one. Nothing read
   them differently, but "exactly the same" is what makes the fast path
   safe to keep: once allowed to differ a little, nothing tells a
   harmless difference from a bug.
4. Each slot's buffer holds the cells of the last frame drawn with it,
   two frames ago. A row that changes now is out of date in both, and
   each catches up when it's next used.
5. Everything guiltty does needs the BEAM running, and the BEAM's boot
   (JIT-compiling the modules it loads) takes ~0.35 s here. Interactive
   mode loads modules as they're first used instead of all at boot, so
   fewer are compiled before the first frame.
6. Between two codepoints whose break property is "Other", UAX #29
   always breaks (GB999). The NIF only makes cells of codepoints that are
   "Other" with "Other" on both sides; the rest goes to
   =String.graphemes/1=, cut where a break is certain.
7. Because the codepoint before it, the skin tone, is not "Other", and
   a rule might join across that edge. The safe cut is the next one,
   between =d= and =e=. (For a skin tone nothing joins after it, but the
   NIF doesn't know rules, only "Other" or not.)
8. It's a pure function with no syscalls: it can't block, it returns in
   well under 1 ms, and a test checks it against Elixir on every
   codepoint. The renderer talks to a GPU driver and a window system and
   can crash in ways no test rules out; a crash there must not take down
   the sessions.
9. It was called at every ground step, also when the next byte was a
   control (ESC, CR, LF) and the answer was 0. Between escape sequences
   that's most calls, and a NIF call costs more than an Elixir step.
   Handling control bytes in Elixir and calling C only when text starts
   made it a win.
10. The profiler times every call, and the timing costs about as much as
    a small function: the 16% was mostly the profiler's own overhead,
    multiplied by a million calls. Only the measured runs say what a
    change gains.
