#+TITLE: Input: from a key press to bash
#+STARTUP: overview

* The path of one key

#+begin_example
  you press "l"
     |
  X11 / Wayland -> SDL3
     |  SDL_EVENT_KEY_DOWN  (key = 'l', mod = 0)
     |  SDL_EVENT_TEXT_INPUT ("l")
     v
  renderer: send KEY and TEXT over stdout
     v
  Guiltty.Window: Protocol.decode -> Keymap.to_bytes
     |  {:key, ?l, 0}  -> nil  (letters come as text)
     |  {:text, "l"}   -> "l"
     v
  Guiltty.Session.Pty.write -> write(master, "l")
     v
  kernel line discipline -> bash (readline) -> echoes "l"
     v
  ... and back through Parser -> Screen -> Window -> renderer
#+end_example

Note that what you see on screen is not what you typed: it's bash's *echo*.
guiltty never draws your keys directly.

* Two kinds of events

SDL reports keyboard input twice, on purpose:

- *Text input* (=SDL_EVENT_TEXT_INPUT=): the character that key produced,
  after Shift, the keyboard layout, dead keys and input methods (see
  "Dead keys and input methods" below). "Shift + 4" arrives as ="$"=. This is what printable keys use.
- *Key events* (=SDL_EVENT_KEY_DOWN=): which key, plus modifier bits. This
  is the only way to see Enter, Backspace, Ctrl+C and so on, which produce
  no text.

The renderer forwards both and lets [[file:../lib/guiltty/keymap.ex][Guiltty.Keymap]] decide. Plain letter
keys map to =nil=, so a letter is never sent twice.

* The simple keys

| Key              | SDL keycode   | Bytes sent          |
|------------------+---------------+---------------------|
| any printable    | (text event)  | the UTF-8 text      |
| Enter, keypad Enter | =0x0D=, =0x40000058= | =\r=       |
| Backspace        | =0x08=        | =0x7F= (DEL)        |
| Tab, Shift+Tab   | =0x09=        | =\t=, =CSI Z=        |
| Escape           | =0x1B=        | =0x1B=              |
| Ctrl+A .. Ctrl+Z | =a= .. =z= + Ctrl | =0x01= .. =0x1A=  |

Why these bytes:

- *Enter is =\r=* because that's what a VT100's Return key sent. The line
  discipline's ICRNL turns it into =\n= for programs that read lines.
- *Backspace is DEL (=0x7F=)*, not BS (=0x08=): modern terminals agree on
  it, and it's what =stty= sets as the erase character (=stty -a= shows
  =erase = ^?=).
- *Ctrl+letter clears the top bits*: =c= is =0x63=, Ctrl+C is =0x03=. That's
  why it's written =^C=, and why Ctrl+I is the same byte as Tab and Ctrl+M
  the same as Enter.

* Keys that send sequences (MVP 3)

Arrows, Home/End, PgUp/PgDn, Insert/Delete and F1-F12 have no byte of
their own, so they send escape sequences. These follow xterm, the
=xterm-256color= entry in terminfo (=infocmp -1 | grep '^\s*k'=):

| Key              | Normal       | Application mode |
|------------------+--------------+------------------|
| Up Down Right Left | =CSI A= .. =CSI D= | =ESC O A= .. =ESC O D= |
| Home End         | =CSI H=, =CSI F= | =ESC O H=, =ESC O F= |
| Insert Delete    | =CSI 2 ~=, =CSI 3 ~= | same         |
| PgUp PgDn        | =CSI 5 ~=, =CSI 6 ~= | same         |
| F1 .. F4         | =ESC O P= .. =ESC O S= | same       |
| F5 .. F12        | =CSI 15 ~= .. =CSI 24 ~= | same     |
| keypad Enter     | =\r=         | =ESC O M=        |

*Application mode* is something programs switch on (=CSI ? 1 h= for the
cursor keys, =ESC == for the keypad); it's terminfo's =smkx=. =vim= and
=less= do it on start. Why two encodings? Historical: the VT100 sent
different codes when its keypad was in application mode, and programs
still ask for it so they can tell an arrow key from someone typing
=ESC [ A=.

With a modifier held, the key gets a parameter m = 1 + Shift(1) + Alt(2) +
Ctrl(4): Ctrl+Right is =CSI 1 ; 5 C=, Shift+PgUp =CSI 5 ; 2 ~=. That's how
=vim= and the shell tell Ctrl+Right (next word) from Right.

* Paste

Ctrl+Shift+V and Shift+Insert paste. The renderer reads SDL's clipboard
and sends the text to Elixir, which turns line breaks into =\r= (like
pressing Enter) and writes it to the shell.

#+begin_example
  without bracketed paste:     l s \r r m   - r f   x \r
                               the shell runs "ls", then "rm -rf x" as it arrives

  with bracketed paste (2004): ESC[200~ l s \r r m - r f x \r ESC[201~
                               the shell knows it's one paste: it shows it,
                               and waits for you to press Enter
#+end_example

Programs turn on bracketed paste with =CSI ? 2004 h=. zsh does by default;
bash does when readline's =enable-bracketed-paste= is on (it's off on this
openSUSE: =bind -v | grep bracketed=). Any =ESC[201~= inside the pasted text
is removed first: otherwise a crafted clipboard could end the paste early
and have the rest run as typed commands.

* The mouse

Programs that want clicks ask for them: =CSI ? 1000 h= for clicks and the
wheel, =1002= to also get drags, =1003= for all motion. =CSI ? 1006 h= picks
the SGR encoding:

#+begin_example
  left click at column 5, row 3:   ESC [ < 0 ; 5 ; 3 M      (m on release)
  wheel down there:                ESC [ < 65 ; 5 ; 3 M
#+end_example

The renderer sends every press, release, wheel turn, and motion into a new
cell; =Guiltty.Keymap.mouse/2= decides, from the modes, what (if anything)
the program gets. Without 1006, the old X10 encoding is used, which can't
go past column 222.

When the program didn't ask, or Shift is held, the mouse is guiltty's:
the left button selects, the middle one pastes, the wheel scrolls back.
That's in [[file:15-scrollback-and-selection.org][the scrollback and selection chapter]].

* Dead keys and input methods

With the US-International layout, the =\'= key doesn't type anything by
itself: it's a *dead key* (=dead_acute=). The next key decides: =e= gives
é, space gives a plain ='=. Spanish =¿= is AltGr+/ on the same layout, and
=ñ= is =~= (=dead_tilde=) then =n=.

Who combines them? Not the terminal. On X11 it's the *input method*: here
=XMODIFIERS=@im=local=, Xlib's built-in one, which follows the compose
rules for your locale (=/usr/share/X11/locale/en_US.UTF-8/Compose=). For
Japanese or Chinese it's a bigger program (IBus, Fcitx) with a candidate
window. On Wayland it's the compositor, through the text-input protocol.

SDL3 talks to all of them once the renderer calls =SDL_StartTextInput=.
What guiltty sees:

#+begin_example
  key            SDL events                               guiltty
  ' (dead)       KEY_DOWN (keycode for '), TEXT_EDITING ""  key: no bytes
  e              KEY_DOWN e, TEXT_INPUT "é"                 sends é
#+end_example

The key events still arrive, but =Keymap= maps plain keys to nothing, so
only the composed text reaches the shell.

While an input method is composing, =SDL_EVENT_TEXT_EDITING= carries the
unfinished text (the *preedit*). The renderer draws it at the cursor,
underlined, for as long as it lasts, without touching the grid: it's
painted over the row for one frame and the row is put back. And it tells
the input method where the cursor is (=SDL_SetTextInputArea=), so a
candidate window opens next to it.

Tested for real: XTest key events (the same events a keyboard makes) on
a private X server with this layout typed =´ e=, =~ n=, AltGr+/ and the
rest, and bash printed =¿Qué tal, señor?=.

* The cheatsheet

Ctrl+Shift+/ (think Ctrl+?) shows every key guiltty has, NvChad-style:
one card per group, each line an action and its keys. The cards sit in a
centered grid: rows balanced (6 cards with room for 5 per row make two
rows of 3), every card in a row as tall as the tallest so their edges
line up, and a bit narrower on an 80-column window so two still fit. It's
built from your config each time, so a key you rebind shows up as you
bound it. Esc, =q= or the same key closes it; arrows, =j=/=k=, PgUp/PgDn and
the wheel scroll it when it's taller than the window.

How it's drawn is the interesting part: the way a program would draw it.
[[file:../lib/guiltty/cheatsheet.ex][Guiltty.Cheatsheet]] writes escape sequences, cursor moves (=CSI row;col H=),
colors (=CSI 38;5;n m=, palette indices, so it follows the theme) and box
characters (=╭─╮│╰╯=), and feeds them through the same parser and terminal
code as the shell's output, into a grid as tall as the sheet:

#+begin_example
  config.keys --> Cheatsheet.render --> "\e[3;2H\e[38;5;8m╭─\e[0m\e[1;38;5;4m Tabs ..."
                                              |
                                  Parser.feed + Terminal.apply
                                              |
                                              v
                                  a Grid: rows of 14-byte cells
                                              |
  Window: a screenful of rows, instead of the tab's  --ROWS-->  renderer
#+end_example

The renderer can't tell the difference: it gets ROWS, as always. While
the sheet is open the Window doesn't take updates from the tab (the shell
keeps running underneath), and keys, text and the mouse go to the sheet.
Closing it re-subscribes to the tab's Screen, which sends every row
again. No C and no protocol change.

* Ctrl+C is not a signal (yet)

guiltty sends only the byte =0x03=. The *kernel* does the rest: the line
discipline sees the =VINTR= character (=^C= by default, see =stty -a=) with
=ISIG= on, and sends SIGINT to the terminal's foreground process group.
That's why Ctrl+C stops =sleep 100= but not bash itself (bash is in a
different process group). In raw mode, as in vim, =ISIG= is off and vim
just receives the byte.

* Escape then a letter

Pressing Escape then =e= sends =\x1be=. Readline reads that as Meta+e and
eats the =e=. Every terminal does this; it's why Escape followed by a key
can act like Alt.

* Questions

1. Why are letters sent from text events and not key events?
2. Why does Ctrl+C stop =sleep 100= but not bash?
3. Why is Backspace =0x7F=?
4. What byte does Ctrl+[ produce, and which key does that match?
5. Who turns =´= then =e= into =é=: the keyboard, the input method, SDL
   or guiltty?
6. The renderer has no idea the cheatsheet exists. How does it end up on
   screen?

** Answers
:PROPERTIES:
:VISIBILITY: folded
:END:

1. Text events already account for Shift, the layout and dead keys. Key
   events only say which key was pressed.
2. The kernel sends SIGINT to the foreground process group, which is
   =sleep='s. Bash is in its own group, and while it waits for a command it
   catches SIGINT itself and just shows a new prompt.
3. It's DEL, the erase character modern systems agree on (=stty= shows
   =erase = ^?=).
4. =[= is =0x5B=; clearing the top bits gives =0x1B=: Escape. (Input v0
   only maps Ctrl+A..Z, so guiltty doesn't send it yet.)
5. The input method (XIM here; IBus, Fcitx or the Wayland compositor
   elsewhere). SDL passes on the result as text input, and guiltty sends
   that text as is.
6. Elixir draws it with escape sequences into a grid, through the same
   parser and terminal code as a program's output, and the Window sends
   those rows in ROWS messages instead of the tab's.
