#+TITLE: The PTY NIF: a pseudoterminal inside the BEAM
#+STARTUP: overview

* What it is

[[file:../c_src/pty_nif.c][c_src/pty_nif.c]] is the only C code that runs inside the BEAM. It does what
[[file:01-pseudoterminals.org][the previous chapter]] described (=openpty=, =fork=, =setsid=, =TIOCSCTTY=,
=exec=), and then hands the master fd to the BEAM and lets an Elixir process,
[[file:../lib/guiltty/session/pty.ex][Guiltty.Session.Pty]], decide when to read and write.

A NIF ("natively implemented function") is a C function that Elixir calls
like any other function. It runs on the scheduler thread that called it, so
two rules matter:

1. *Never block.* A scheduler stuck in =read()= stops every Elixir process
   scheduled on it. So the master fd is non-blocking.
2. *Never crash.* A segfault in a NIF kills the whole VM. So the NIF is small,
   and all decisions are made in Elixir.

* The functions

| Elixir                                 | Does                                  |
|----------------------------------------+---------------------------------------|
| =PtyNif.open(path, argv, env, c, r, cwd)= | posix_openpt, fork, chdir, exec; ={:ok, pty, pid}= |
| =PtyNif.foreground(pty)=              | tcgetpgrp: the foreground job's group (chapter 18) |
| =PtyNif.read(pty)=                     | one non-blocking read                 |
| =PtyNif.write(pty, bytes)=             | one non-blocking write                |
| =PtyNif.select_read(pty)=              | "tell me when it's readable"          |
| =PtyNif.select_write(pty)=             | "tell me when it's writable"          |
| =PtyNif.close(pty)=                    | close the master (hangs up bash)      |
| =PtyNif.wait(pty)=                     | has the child exited? never blocks    |
| =PtyNif.kill(pty, signal)=             | send a signal to the child            |

=open= runs on a *dirty I/O scheduler* (a separate thread pool for slow NIFs),
because =fork= copies the page tables of the whole BEAM and that can take a
while.

* Resources: a C struct that Elixir can hold

The master fd and the child live in a =struct pty= wrapped in a *NIF
resource*. Elixir sees an opaque reference; the C side gets the struct back
on every call.

#+begin_example
  Elixir (Pty process state)           C heap (owned by the BEAM)
  +--------------------------+         +--------------------------+
  | pty: #Reference<...> ----+-------->| struct pty               |
  | os_pid: 219202           |         |   lock                   |
  +--------------------------+         |   fd    = 23 (master)    |
                                       |   pidfd = 24 (the child) |
                                       +--------------------------+
                                       destructor runs when the last
                                       Elixir reference is garbage
#+end_example

The child is held as a *pidfd*, not a pid (see "Surprise: the BEAM ignores
SIGCHLD", below). The *lock* is there because a resource can be used from
two processes at once: the Pty process, and later the task that reaps its
shell. Each runs on its own scheduler thread, so without the lock one could
close the fd while the other reads it.

The destructor ([[file:../c_src/pty_nif.c::pty_dtor][pty_dtor]]) is a safety net: if the Pty process died
without cleaning up, it closes the fd and SIGKILLs the child through the
pidfd. If the child is already gone, that signal goes nowhere.

* enif_select: no reader thread

The classic way to read from an fd without blocking is a thread sitting in
=read()=. guiltty doesn't need one: the BEAM already runs a =poll=-like loop
for its own sockets, and =enif_select= adds our fd to it.

#+begin_example
  Pty process                 NIF                    BEAM poll loop
  -----------                 ---                    --------------
  select_read(pty) -------->  enif_select(fd, READ) -> add fd to poll set
  (handles other messages)
                                                      fd readable!
  <------------------- {:select, pty, :undefined, :ready_input}
  read(pty) --------------->  read(fd) = 4096 bytes
  read(pty) --------------->  read(fd) = 312 bytes
  read(pty) --------------->  read(fd) = EAGAIN -> :eagain
  select_read(pty) -------->  (armed again: it fires only once)
#+end_example

The select fires once. The Pty process only re-arms it when there's a parser
to send bytes to. Until then, bash's output stays in the kernel's PTY buffer;
when that fills up, bash blocks on its own =write()=. That's the start of
MVP 4's kernel backpressure.

** Closing a selected fd
You may not just =close()= an fd that's in the BEAM's poll set: the BEAM
might be polling it at that moment, and the number could be reused by a new
fd. Instead [[file:../c_src/pty_nif.c::nif_close][close/1]] calls =enif_select(..., ERL_NIF_SELECT_STOP)=, and the
BEAM calls our =stop= callback ([[file:../c_src/pty_nif.c::pty_stop][pty_stop]]) when it's safe. That's where
=close()= really happens.

* Forking from a multithreaded program

A single-threaded program can call almost anything after =fork=. The BEAM
has dozens of threads, and =fork= copies only the calling one:

#+begin_example
  BEAM before fork                     child after fork
  +--------------------------+         +--------------------------+
  | scheduler 1 (calls fork) |   --->  | scheduler 1 (the child)  |
  | scheduler 2 (in malloc,  |         |                          |
  |   holds malloc lock)     |         |  malloc lock: LOCKED,    |
  | dirty io 1, ...          |         |  and no thread will ever |
  +--------------------------+         |  unlock it               |
                                       +--------------------------+
#+end_example

So the child calls only async-signal-safe functions until =execve= replaces
it with bash ([[file:../c_src/pty_nif.c::exec_child][exec_child]]). Everything it needs (argv, envp, the path) is
prepared before =fork=. The NIF uses =execve= with a full path, which Elixir
finds with =System.find_executable/1=, because =execvp= searches =PATH= and
isn't on the safe list.

Three more things the child does because it's forked from the BEAM:

- *Resets signals.* The BEAM blocks and ignores some signals, and both survive
  =execve=. Without the reset, every program you ran in guiltty would start
  with, for example, SIGPIPE ignored. A test checks bash's =SigIgn= is zero.
- *Closes every other fd* with =close_range(3, ~0U, 0)=, so bash doesn't
  inherit the BEAM's sockets or another tab's PTY.
- *Changes directory* with =chdir(2)= (async-signal-safe) when given one,
  so a new tab starts where the current tab's shell is (chapter 16). If
  the directory is gone, the shell starts where the BEAM is.
- Both PTY fds are close-on-exec from the moment they exist, so no other
  program the BEAM starts inherits them. A stray copy of the slave would
  keep the master from ever reporting the end (see [[file:01-pseudoterminals.org][chapter 1]], "The end").
  The master comes from =posix_openpt(O_CLOEXEC | O_NONBLOCK ...)=, and the
  slave from =ioctl(master, TIOCGPTPEER, O_CLOEXEC ...)=, which opens
  /this/ master's slave without looking up a path in =/dev/pts=. (Until
  v0.12.4, =openpty= opened them and a second call set close-on-exec:
  for a moment in between, a fork on another thread could inherit them.)

* Surprise: the BEAM ignores SIGCHLD

The first live run logged =ended: {:error, :echild}=. The BEAM sets SIGCHLD
to "ignore", and Linux has a special rule for that (=waitpid(2)=, NOTES):
children are reaped automatically and never become zombies, but their exit
status is thrown away.

#+begin_example
  bash running   waitpid(pid, WNOHANG) = 0          -> :running
  bash exits     kernel reaps it right away
  afterwards     waitpid(pid, WNOHANG) = -1 ECHILD  -> :gone
#+end_example

So =wait/1= returns =:gone= instead of an exit code. One consequence matters
for safety: once bash is gone, its pid is free, and the next process may
get it, maybe another tab's shell (a child of the same BEAM). A
=kill(pid, SIGKILL)= sent a moment too late would hit that one.

So the NIF never signals a pid. Right after =fork=, it asks for a *pidfd*
(=pidfd_open(2)=): a file descriptor that means this one process, alive
or dead. Signals go through it (=pidfd_send_signal=), and so does waiting
(=waitid(P_PIDFD, ...)=). Once the child is gone, a signal through its
pidfd fails with ESRCH; it can't reach anyone else.

#+begin_example
  bash running   waitid(P_PIDFD, fd, WNOHANG): si_pid = 0  -> :running
  bash exits     kernel reaps it right away
  afterwards     waitid(P_PIDFD, fd, WNOHANG) = -1 ECHILD   -> :gone
                 kill through the pidfd                     -> {:error, :esrch}
#+end_example

There's one moment the pid is still used: =pidfd_open(pid)= right after
=fork=. For that to pick up a stranger, the child would have to exit and
its pid come round again (out of =pid_max=, 4 million here) between two
lines of the parent. glibc doesn't offer a =fork= that returns a pidfd
yet; =clone3= with =CLONE_PIDFD= does, at the cost of skipping glibc's
=fork=.

* The Pty process

[[file:../lib/guiltty/session/pty.ex][Guiltty.Session.Pty]] wraps all of this:

- The shell gets guiltty's environment *minus the VM's own variables*:
  the Erlang runtime's (=BINDIR=, =ROOTDIR=, =EMU=, =PROGNAME=) and the
  release start script's (=RELEASE_*=). Two reasons. Another Mix release
  started from the shell would read =RELEASE_NODE= as its own node name and
  collide with guiltty's (that's how =extop= failed). And =RELEASE_COOKIE=
  used to be the key to run code on guiltty's node: no program in your
  shell should be able to read it. (Since v0.12.4 it's empty, and the key
  lives in =~/.erlang.cookie=; chapter 20.)
- It runs *your* shell: =$SHELL=, or your login shell from the user
  database (=getent passwd $USER=, which asks NSS, so LDAP users work too),
  or bash, or =/bin/sh=, the first that is an executable file.
- On start it opens the PTY with =TERM=xterm-256color= and
  =COLORTERM=truecolor= (MVP 1 used =TERM=dumb=), but doesn't read yet.
- =resize/3= calls the NIF's =resize=, an =ioctl(TIOCSWINSZ)= ([[file:09-resize.org][the resize
  chapter]]).
- When the parser attaches, it arms =select_read=.
- On =:ready_input= it reads up to 16 chunks, sends each to the parser as
  ={:pty_data, bytes}=, then re-arms.
- Writes go through a =pending= buffer: if the kernel takes only part of it,
  it waits for =:ready_output= and writes the rest.
- On =:eof= (EIO), it closes the master, waits for bash to go, and stops with
  ={:shutdown, status}=, which ends the session.
- On shutdown, =terminate/2= closes the master (the kernel sends SIGHUP)
  and returns at once. A short-lived helper process holds on to the NIF
  resource and gives the shell half a second, then sends SIGHUP and finally
  SIGKILL. The Pty itself must die quickly: see "Killing a supervisor" in
  [[file:04-screen-and-grid.org][chapter 4]].

* Questions

1. Why is the master fd non-blocking?
2. Why can't the NIF just =close(fd)= after an =enif_select=?
3. What could go wrong if the child called =malloc= after =fork=?
4. Why does =wait/1= return =:gone= instead of an exit code?
5. Why does the Pty process wait for a parser before reading?
6. Why does the NIF signal the child through a pidfd instead of its pid?
7. Why doesn't =pty_stop= take the lock?

** Answers
:PROPERTIES:
:VISIBILITY: folded
:END:

1. A NIF runs on a scheduler thread. A blocking =read= would freeze every
   Elixir process on that scheduler until bash printed something.
2. The BEAM may be polling that fd number right then. =ERL_NIF_SELECT_STOP=
   asks it to remove the fd first and call =stop=, where it's safe to close.
3. Another BEAM thread might have held malloc's lock during =fork=. The child
   gets the lock still locked, with no thread to unlock it: a deadlock.
4. The BEAM ignores SIGCHLD, so the kernel reaps children immediately and
   discards their status. =waitpid= then fails with ECHILD.
5. Otherwise the first bytes (the prompt) would be read with nobody to send
   them to. Not reading leaves them safely in the kernel buffer.
6. The kernel reaps the child as soon as it exits, and its pid can then go
   to another process, maybe another tab's shell. A pidfd always refers to
   the same process; once that process is gone, signals fail with ESRCH.
7. The BEAM may call it from inside =enif_select=, which =close= calls
   while holding the lock: taking it again would deadlock. It only closes
   the fd it's given; =close= has already marked the pty closed.
