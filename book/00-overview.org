#+TITLE: Overview: what a terminal emulator actually is
#+STARTUP: overview

* The short version

A terminal emulator does not run your commands. Bash runs them. The terminal
only does two jobs:

1. turn *bytes* coming from bash into *pixels* (text, colors, a cursor), and
2. turn *keys* you press into *bytes* going to bash.

Between the terminal and bash sits a kernel device, the pseudoterminal (PTY),
that makes bash believe it is talking to a real 1970s hardware terminal.
Everything else in guiltty is plumbing around those two jobs.

* The whole pipe

This is guiltty at MVP 1. Every later MVP thickens the same pipe instead of
adding new boxes.

#+begin_example
                        BEAM (one OS process, many Elixir processes)
  +-------------------------------------------------------------------------+
  |                                                                         |
  |   Session (rest_for_one)                                                |
  |   +---------+   bytes   +--------+   commands   +--------+              |
  |   |   Pty   | --------> | Parser | -----------> | Screen |              |
  |   | (NIF fd)|           +--------+              | (grid) |              |
  |   +---------+                                   +--------+              |
  |      ^  |                                           | changed rows      |
  |      |  |                                           v                   |
  |      |  |  key bytes                           +--------+               |
  |      |  +<-------------------------------------| Window |               |
  |      |                                         +--------+               |
  +------|-------------------------------------------|---^------------------+
         | master fd                     port stdin  |   | port stdout
         |                               (rows)      v   | (key events)
  +------|------+                               +-------------------+
  |  kernel PTY |                               | guiltty_vk        |
  |  /dev/pts/N |                               | (separate C proc) |
  +------|------+                               | SDL3 + Vulkan     |
         | slave fd 0,1,2                       +-------------------+
  +------v------+                                     |
  |    bash     |                                     v
  +-------------+                                  pixels
#+end_example

Three pieces are C, the rest of the program is Elixir. That doesn't make
the C small: it's about 5,600 lines (plus 320 of shaders) next to about
6,500 of Elixir, so a bit under half. Most of it is the renderer, since
fonts, glyphs and two GPU APIs take a lot of code.

| Part          | Language | Lines (about) |
|---------------+----------+---------------|
| everything that decides: parser, screen, tabs, windows, config | Elixir | 6,500 |
| the renderer: core 3,000, Vulkan 1,200, OpenGL 400 | C  | 4,500 |
| the PTY NIF   | C        | 530           |
| the client    | C        | 250           |
| fuzz targets and tools (development only) | C | 280 |

(Counted with =wc -l=, comments and blank lines included, without the
generated width table; the tests are another 3,600 lines of Elixir.)

- *The PTY NIF* lives inside the BEAM because it has to make syscalls
  (=openpty=, =fork=, =read=, =write=). It is kept small (about 530 lines),
  since a crash there takes down the whole VM.
- *The renderer* is a separate program. If it segfaults, only the window dies;
  bash and the screen contents survive in Elixir and can be redrawn. It
  comes in two builds with the same core: =guiltty_vk= (Vulkan, the
  default) and =guiltty_gl= (OpenGL, the fallback). See [[file:19-vulkan.org][chapter 19]].
- *The client* (since MVP 15) is the =guiltty= command itself: a small
  program that asks the running guiltty for a window over a Unix socket,
  or starts guiltty. It decides nothing. See [[file:23-client-server.org][chapter 23]].

The pipe above is still there, once per tab. Around it, MVP 4 and later
added tabs that outlive windows, MVP 13 independent windows, and MVP 15
the client:

* Questions

1. Which program executes =ls= when you type it in guiltty?
2. Why is the renderer a separate OS process instead of a NIF?
3. Which way do bytes flow through the master fd, and which way do pixels flow?

** Answers
:PROPERTIES:
:VISIBILITY: folded
:END:

1. Bash forks and execs =ls=. guiltty only moves bytes and draws them.
2. A crash in a NIF kills the whole BEAM, sessions included. A crashed port
   program only closes its port, and Elixir can restart it and redraw.
3. Both ways: bash's output is read from the master, and your keys are
   written to it. Pixels only flow out, from the renderer to the screen.
