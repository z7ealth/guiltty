#+TITLE: Testing a terminal with real bytes
#+STARTUP: overview

* Why real bytes

It's easy to write a test with the escape sequence you /think/ =ls= sends.
It's more useful to record what =ls= really sends, and check that guiltty
draws what a real terminal would. guiltty's tests do both, in layers:

| Layer                | Tests                                  | Where                          |
|----------------------+----------------------------------------+--------------------------------|
| parser               | sequences, limits, properties          | [[file:../test/guiltty/parser_test.exs][parser_test.exs]]   |
| grid and terminal    | each cursor, erase and resize case     | [[file:../test/guiltty/grid_test.exs][grid_test.exs]]       |
| SGR                  | every attribute and color form         | [[file:../test/guiltty/sgr_test.exs][sgr_test.exs]]         |
| real programs        | recorded fixtures vs. snapshots        | [[file:../test/guiltty/golden_test.exs][golden_test.exs]]   |
| NIF, session, window | a real bash and a real (headless) renderer | session_test, window_test |

* Recording fixtures

[[file:../test/fixtures/record.sh][test/fixtures/record.sh]] runs a command under =script(1)= in an 80x24
=xterm-256color= PTY and keeps exactly the bytes it wrote:

#+begin_src sh
test/fixtures/record.sh ls_color 'ls --color=always -l'
test/fixtures/record.sh less_page 'less -R /usr/etc/services' ' ' ' ' b q
#+end_src

Extra arguments are keys, typed after a pause so the program has drawn
first. Lessons learned while recording:

- Pause long enough. =man= takes a moment to format; keys typed before
  =less= starts get lost, and the recording hangs.
- openSUSE's =man ls= first asks which =ls= you mean (=ls(1)= or =ls(1p)=):
  use =man 1 ls=.
- =/etc/services= moved to =/usr/etc/services= on openSUSE.
- The recorder runs programs with =LC_ALL=C.UTF-8=. Fixtures from before
  MVP 5 were recorded with =LC_ALL=C=, which kept them mostly ASCII.

* Golden snapshots

[[file:../test/guiltty/golden_test.exs][golden_test.exs]] feeds each =NAME.bytes= through the parser and the terminal
at 80x24, and compares the result to =NAME.txt=:

#+begin_example
$ git status
...the screen text, 24 lines...
--- cursor 23,0 visible
--- styles
1 7-18 bold
4 0-3 fg=1
9 0-79 bg=#336699
#+end_example

The styles section lists every run of non-default cells, so a broken color
shows up in the diff, not just broken text. Each fixture is also fed one
byte at a time, which must give the same screen.

To update snapshots after an intended change:

#+begin_src sh
GUILTTY_UPDATE_GOLDEN=1 mix test test/guiltty/golden_test.exs
git diff test/fixtures/      # read it: this is the review
#+end_src

* Checking the snapshots against another emulator

A snapshot only proves guiltty does what it did yesterday. To check it's
/right/, the MVP 2 snapshots were compared, cell by cell, with
[[https://github.com/selectel/pyte][pyte]], an independent VT emulator written in Python: same bytes, same
80x24 screen, then compare the text, the cursor, bold, underline, inverse
and both colors. All 13 fixtures matched. The two differences found were
representation only (pyte names =31= "red" but writes =38;5;1= as a hex
value; guiltty stores both as palette 1), and UTF-8 (pyte decoded it;
guiltty showed =?= before MVP 5).

* Full-screen programs (MVP 3)

=vim= and =less= draw on the alternate screen and switch back when they
quit, so the final screen alone says little. For those fixtures the
snapshot first records the alternate screen just before the program left
it, then the main screen it returned to.

pyte has no alternate screen, so the comparison feeds it the bytes up to
that moment. Comparing against =vim= turned up more gaps in pyte than in
guiltty, each checked against the spec and xterm:

- pyte ignores =ESC ( 0= (line drawing) in UTF-8 mode, and has no =CSI s= /
  =CSI u= or REP. Those three fixtures are expected to differ.
- pyte crashes on =CSI > 4 ; 2 m=, prints the contents of DCS strings, and
  prints the final byte of CSI sequences with intermediates (=CSI 0 % m=).
  vim sends all three while probing the terminal; they're stripped before
  feeding pyte.
- pyte gives *different results depending on whether you read its screen*:
  it stores lines sparsely, and some line operations behave differently on
  a sparse line. Reading the screen after every byte keeps it consistent.

Lesson: a reference implementation is evidence, not truth. When two
emulators disagree, find the byte where they diverge and check the spec.

* tmux as the reference

tmux is itself a complete terminal emulator: it parses everything its
programs send and keeps a screen per pane. That makes it a better
reference than pyte for full-screen programs:

#+begin_example
  tmux -L reference new-session -d -x 80 -y 24 'htop'   a hidden 80x24 pane
  tmux pipe-pane -o 'cat > htop.bytes'                  every byte htop writes
  tmux send-keys Down Down F5                           drive it
  tmux capture-pane -p                                  what tmux shows: the reference
#+end_example

Then guiltty renders =htop.bytes= and the two screens are compared row by
row, plus the cursor. (Before MVP 5, guiltty's =?= for non-ASCII and its
ASCII line-drawing lookalikes counted as matching; now the snapshots have
the real characters.) htop, vim, less, and tmux
itself (one tmux running inside another) all match exactly. The htop and
tmux recordings are fixtures now.

* Property tests

[[https://hexdocs.pm/stream_data][StreamData]] generates inputs instead of us writing them:

- *Random bytes never crash the parser.*
- *Chunking doesn't matter*: random mixes of real sequences, cut at random
  points, parse to the same commands as when fed whole.

* Renderer replay (MVP 10)

The renderer can be tested without Elixir too. =GUILTTY_RECORD=file=
makes the Window save every port message it sends; =--replay file
--screenshot out.ppm= plays them into a renderer and saves the last
frame. [[file:../test/fixtures/replay/session.msgs][session.msgs]] is one such recording, and
[[file:../test/guiltty/renderer_replay_test.exs][renderer_replay_test.exs]] replays it through both backends, under the
sanitizers (and Vulkan's validation layers), and checks that OpenGL and
Vulkan draw the same pixels. Details in [[file:19-vulkan.org][chapter 19]].

A replay draws one frame per ROWS message, as a live window does, so it
also tests damage tracking: thirty small updates must end on exactly the
picture one whole update gives, in each backend (chapter 22).

* Older Elixir and Erlang

guiltty is written on the newest Elixir and Erlang, but the people who
install it often have what their distribution ships. The oldest it
supports is *Elixir 1.18 on Erlang/OTP 26*. Every pair below built
guiltty with =--warnings-as-errors=, passed the whole suite, and (where
marked) built a release that starts:

| Elixir | Erlang/OTP | Tests            | Release |
|--------+------------+------------------+---------|
| 1.20.4 | 29         | 295, all passed  | yes     |
| 1.19.7 | 28         | 295, all passed  | yes     |
| 1.19.7 | 26         | 295, all passed  | -       |
| 1.18.4 | 26         | 295, all passed  | yes     |

=mix.exs= enforces the Elixir side (=elixir: "~> 1.18"=); nothing
enforces the Erlang side, so the README states it.

** Running the suite on another version

asdf installs versions side by side, and two variables pick them for
one command, without changing your default. Build in a copy of the
project, so its =_build= and =deps= stay yours:

#+begin_src sh
asdf install erlang 26.2.5.21          # builds from source, ~10 min
asdf install elixir 1.18.4-otp-26
mkdir /tmp/g && git ls-files -z | xargs -0 cp --parents -t /tmp/g
cd /tmp/g
export ASDF_ERLANG_VERSION=26.2.5.21 ASDF_ELIXIR_VERSION=1.18.4-otp-26
mix local.hex --force && mix local.rebar --force && mix deps.get
mix compile --warnings-as-errors && mix test
MIX_ENV=prod mix release && _build/prod/rel/guiltty/bin/guiltty eval 'IO.puts(:ok)'
#+end_src

(=KERL_BUILD_DOCS=no= and =KERL_CONFIGURE_OPTIONS="--without-javac
--without-wx --without-odbc"= make the Erlang build shorter.)
=mix format --check-formatted= is the one check left out: each Elixir's
formatter lays a few lines out its own way, and the code is formatted
for the newest.

** What the old versions found

- *A NIF built for another Erlang.* Switching Erlang in the project
  itself (=asdf set=) and building again kept =priv/pty_nif.so= from
  before: =make= compares file times, and no source had changed. But a
  NIF is built against one Erlang's =erl_nif.h=, and OTP 26 refused the
  one built for OTP 29 ("NIF library needs erts-14.0 or newer"). The
  NIF now also depends on a stamp, =_build/erts/erts-VERSION=, named
  after the Erlang it was built for: a different Erlang means a missing
  stamp, and a rebuild ([[file:../Makefile::ERTS_STAMP][Makefile]]). This is also why the
  section above builds in a copy.

- *A line over the limit, on OTP 26.* =gen_tcp= in line mode with a
  =packet_size= returns ={:error, :emsgsize}= from OTP 27 on. OTP 26
  hands the long line out in pieces of 1,460 bytes, none ending in a
  line break. The Launcher took each piece for a line and answered
  "request incomplete" after its 2 s timeout. Safe (it reads at most 16
  lines), but slow and wrong. Now a piece without a line break is
  "line too long" at once, on every OTP ([[file:../lib/guiltty/launcher.ex::read_lines][read_lines]]).
- *A test that could fail on any version.* The flood test waited for
  =FLOOD-DONE= on screen, but the command it typed, =seq ...; echo
  FLOOD-DONE=, shows that too. On a busy machine the shell's echo came
  before the first sample, and the test saw "done" with nothing
  measured. The slower OTP made it show; it now waits for a line that
  /starts/ with =FLOOD-DONE=.

* Loot

- =script(1)= from util-linux.
- StreamData's =check all= and generators.
- "Golden master" (or snapshot) testing.
- Elixir's compatibility table ("Compatibility and deprecations" in the
  Elixir docs): which Erlang/OTP each Elixir runs on.
- =inet:setopts/2=, =packet= and =packet_size=: what line mode does with
  a line over the limit.

* Questions

1. Why record fixtures instead of writing the escape sequences by hand?
2. What does a snapshot prove, and what doesn't it?
3. Why feed each fixture one byte at a time too?
4. Why test old versions in a copy of the project, not in it?
5. Why did the flood test pass on OTP 29 and fail on OTP 26?

** Answers
:PROPERTIES:
:VISIBILITY: folded
:END:

1. Real programs send things you wouldn't think of (=ESC 7= around titles,
   =ESC[22;0;0t=, =ESC(B=). Hand-written tests only test what you already
   know.
2. That guiltty draws the same as when the snapshot was taken. Not that it
   was right then; that needs a reference, like a real terminal or pyte.
3. To catch state that doesn't survive a split read: a read can end
   anywhere, and the screen must not change because of it.
4. =_build= and =deps= are compiled for one Elixir and Erlang. Building
   with another in place would recompile them for it, and your next
   =mix test= would recompile everything back (or trip on beams it
   can't load).
5. It wasn't the OTP: the test raced the shell's echo of the command,
   which contains =FLOOD-DONE=. It usually lost the race by a few
   milliseconds; on a slower, busier run it won, and the test stopped
   before taking a sample.
