#+TITLE: Resize: from a dragged window to SIGWINCH
#+STARTUP: overview

* Who knows the size

Three places need to agree on how big the terminal is:

| Who          | Knows it as                     | Why it needs it                    |
|--------------+---------------------------------+------------------------------------|
| the renderer | pixels, so it works out cells   | it owns the window                 |
| the Screen   | the grid's columns and rows     | where text wraps, where LF scrolls |
| the kernel   | =struct winsize= on the PTY      | programs ask it: =tput cols=       |

Since v0.18 there's a fourth thing to agree on: how big one *cell* is in
pixels. Programs that draw images (yazi, chafa, timg) need it to know how
many cells a picture covers. See "Pixels too" below.

The renderer is the only one that sees the window, so it starts the chain.

* The chain

#+begin_example
  you drag the window edge
     |
  SDL: WINDOW_PIXEL_SIZE_CHANGED 1100 x 420
     |
  renderer: cols = (1100 - 2*6) / 11 = 98     rows = (420 - 2*6) / 23 - 1 = 16
     |      (since MVP 4 one row is the tab bar; this example predates it: read 17 as 16)
     |      clears its cell mirror to 98x17, sends RESIZE 98 17 (cell 11x23)
     v
  Window ----> Tabs.resize(98, 17, {11, 23}) -> Session.resize(id, ...) for every tab
                 |
                 |-- 1. Screen.resize: Grid.resize (no reflow), every row dirty,
                 |      sends a full update tagged 98x17 -----------------> renderer draws
                 |
                 `-- 2. Pty.resize: ioctl(master, TIOCSWINSZ, {17, 98, 1078, 391})
                          |
                        kernel: size changed -> SIGWINCH to the foreground job
                          |
                        bash / less / man: ioctl(TIOCGWINSZ) -> redraw for 98x17
#+end_example

The order inside =Session.resize= matters: the grid has its new size
*before* SIGWINCH goes out, so the program's redraw lands on a grid that
already fits it.

* Updates from before the resize

Messages already on their way can describe the old size:

#+begin_example
  Screen sends ROWS 80x24 ...     renderer resizes to 98x17
                     \___________ arrives late: "80x24"? not my size -> dropped
  Screen sends ROWS 98x17 (full)  -> applied
#+end_example

That's why every ROWS message carries the grid size it describes. Dropping
a stale update is safe because the resize always produces a full update at
the new size right after.

* No reflow

=Grid.resize= doesn't re-wrap text. Rows are cut or padded on the right,
and added or removed at the bottom. One exception: if shrinking would push
the cursor off the screen, rows are removed from the top instead, so the
line you're typing on stays. Reflow (re-wrapping long lines) is an NG+
quest, and only really matters once there's scrollback.

* The kernel side

=TIOCSWINSZ= stores the size in the terminal and, if it changed, sends
SIGWINCH to the terminal's *foreground process group*: the job you're
running, not every process. Programs that care install a SIGWINCH handler
and ask for the size again with =TIOCGWINSZ=. bash does it to know where to
wrap your command line; =less= and =man= redraw the page.

Try it in guiltty: run =less= on a big file, resize the window, and watch
it redraw. Or check what programs see:

#+begin_src sh
tput cols; tput lines; stty size
#+end_src

* Pixels too

=struct winsize= has always had two more fields than rows and columns:

#+begin_src c
struct winsize {
    unsigned short ws_row, ws_col;        /* cells */
    unsigned short ws_xpixel, ws_ypixel;  /* the text area in pixels, 0 = unknown */
};
#+end_src

The kernel never reads the pixel fields. It only stores them for programs
to ask. For years most terminals left them at 0. Programs that draw images
need them: yazi asks the kernel first, and the terminal itself if the
kernel says 0. Here is what yazi 26.8 writes when it starts, recorded from
a PTY:

#+begin_example
ESC [ > q                               XTVERSION: who are you?
ESC _ G i=31,s=1,v=1,a=q,t=d,f=24;AAAA ESC \    Kitty graphics: can you draw?
ESC [ 16 t                              XTWINOPS: how big is a cell, in pixels?
ESC [ 0 c                               DA1, last: answers come in order, so
                                        when this one arrives, every other
                                        question has had its chance
#+end_example

So the renderer, the only one that knows the font, sends the cell size with
every RESIZE. It also sends one at startup, even when the grid already
fits, and after a new font changes the cell, even when cols and rows stay
the same. From there it goes two ways:

- *the kernel*: =Pty.resize= fills =ws_xpixel= = cols × cell width and
  =ws_ypixel= = rows × cell height (0 if that wouldn't fit an unsigned
  short);
- *the Screen*: the grid keeps =cell_pixels=, and =Guiltty.Terminal=
  answers the XTWINOPS questions from it:

| Question                     | Sequence    | guiltty answers (98x17, cell 11x23) |
|------------------------------+-------------+--------------------------------------|
| text area in pixels          | =CSI 14 t=  | =CSI 4 ; 391 ; 1078 t= (height;width) |
| one cell in pixels           | =CSI 16 t=  | =CSI 6 ; 23 ; 11 t=                   |
| grid in cells                | =CSI 18 t=  | =CSI 8 ; 17 ; 98 t=                   |

Until a renderer has said, the pixel questions get no answer at all. A
program that gets no answer falls back to something else. A made-up answer
would make it draw images at the wrong size.

Check it yourself in guiltty:

#+begin_src sh
printf '\e[16t'; IFS= read -rsd t px; echo "${px#*[}"     # 6;23;11
python3 -c 'import fcntl,struct,termios; print(struct.unpack("4H", fcntl.ioctl(0, termios.TIOCGWINSZ, bytes(8))))'
#+end_src

* Loot

- =ioctl_tty(2)=: =TIOCGWINSZ=, =TIOCSWINSZ=; =struct winsize='s pixel
  fields.
- XTerm control sequences (ctlseqs): "Window manipulation (XTWINOPS)",
  =CSI Ps t= with Ps = 14, 16, 18.
- =signal(7)=: SIGWINCH.
- =tput(1)=, =stty(1)=.

* Questions

1. Why does the renderer decide the new size, and not Elixir?
2. Who receives SIGWINCH?
3. Why resize the grid before the PTY?
4. Why is it safe to drop a ROWS message of the wrong size?
5. The window didn't change size, but you zoomed in. Why does a RESIZE
   still go out?
6. Before the renderer has said anything, why doesn't guiltty answer
   =CSI 16 t= with a guess?

** Answers
:PROPERTIES:
:VISIBILITY: folded
:END:

1. Only the renderer knows the window's pixels and the font's cell size.
2. The terminal's foreground process group.
3. So the program's redraw, triggered by SIGWINCH, already finds a grid of
   the right size.
4. A resize always ends with a full update at the new size.
5. A bigger font means a bigger cell. Programs that draw images need the
   new cell size, even if cols and rows came out the same.
6. A wrong answer makes images the wrong size. No answer makes the
   program fall back to something that works.
