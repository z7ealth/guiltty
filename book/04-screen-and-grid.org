#+TITLE: The screen and the grid
#+STARTUP: overview

* The grid

[[file:../lib/guiltty/grid.ex][Guiltty.Grid]] is the screen as data: rows of cells, a cursor, and the
*pen* (the style new text is written with). A cell is 14 bytes (glyph,
attributes, foreground, background; see [[file:08-colors.org][the colors chapter]] and
[[file:13-unicode.org][the Unicode chapter]]), and each row is one binary of =cols= cells.

#+begin_example
  lines (a tuple of rows)                         cursor     pen
  0  [$][ ][e][c][h][o][ ][h][i] ... [ ]          row 2      attrs 0
  1  [h][i][ ][ ][ ][ ][ ][ ][ ] ... [ ]          col 2      fg default
  2  [$][ ][ ][ ][ ][ ][ ][ ][ ] ... [ ]                     bg default
      \__ each [x] is <<glyph::32, attrs::16, fg::32, bg::32>>, 14 bytes
#+end_example

A row being a plain binary is handy: it's already exactly what the renderer
needs, so a changed row goes straight into a port message.

* From commands to the grid

The parser only knows syntax. [[file:../lib/guiltty/terminal.ex][Guiltty.Terminal]] decides what each command
means and calls the grid:

| Command                  | Name          | Effect                                       |
|--------------------------+---------------+----------------------------------------------|
| ={:print, s}=            |               | write =s= with the pen, wrapping at the edge |
| =:cr= =:lf= =:bs= =:ht=  | C0            | column 0; down (scroll at bottom); left; tab |
| =CSI n A= / =B= / =C= / =D= | CUU CUD CUF CUB | move up, down, right, left n           |
| =CSI n E= / =F=          | CNL CPL       | down / up n lines, to column 1              |
| =CSI n G=, =CSI n d=     | CHA VPA       | to column n, to row n                        |
| =CSI r;c H=              | CUP           | to row r, column c (1-based)                 |
| =CSI n J=                | ED            | erase below (0), above (1), all (2)          |
| =CSI n K=                | EL            | erase right (0), left (1), the line (2)      |
| =CSI n X=                | ECH           | erase n cells, cursor stays                  |
| =CSI ... m=              | SGR           | change the pen ([[file:08-colors.org][colors]])                   |
| =CSI ? 25 h= / =l=       | DECTCEM       | show / hide the cursor                       |
| =ESC D=, =ESC E=, =ESC M= | IND NEL RI   | index, next line, reverse index              |
| =ESC c=                  | RIS           | full reset                                   |

Positions are 1-based on the wire and 0-based in the grid, and a missing or
0 count means 1. Moves clamp at the edges. Everything else (the alternate
screen, scroll regions, cursor save) is ignored until MVP 3. Reverse index
came early because =less= uses it to scroll back.

Note that =:lf= doesn't go back to column 0. Bash's =\n= reaches us as =\r\n=
because the line discipline's ONLCR adds the =\r=.

** Scrolling
A line feed on the last row drops row 0 and adds a blank row at the bottom.
Every row moved, so every row is marked dirty.

** The pending wrap
After writing into the last column, the cursor sits *past* it, at column 80.
The wrap happens only if another printable character arrives:

#+begin_example
  print "0123456789" on a 10-column grid:
  |0123456789|_      cursor col 10: wrap pending
  then CR LF:        -> next row, no blank line in between
  then "x" instead:  -> wraps first, "x" lands at the start of the next row
#+end_example

Without this, every command whose output is exactly 80 columns wide would
leave an empty line under it. xterm and every terminal since the VT100 work
this way.

* Dirty rows

The grid remembers which rows changed. =take_dirty/1= returns them and
clears the set, so the Screen only sends what changed.

* The Screen process

[[file:../lib/guiltty/session/screen.ex][Guiltty.Session.Screen]] holds the grid and is the *authoritative* copy of
what's on screen. After each batch of commands it sends
={:screen_update, id, %{size:, rows:, cursor:, cursor_visible:}}= to its
subscribers: the =Window=, which forwards them to the renderer (see
[[file:05-port-protocol.org][the port protocol]]). A new subscriber first gets every row, which is how
a restarted renderer redraws.

From iex:

#+begin_src elixir
Guiltty.Session.write(Guiltty.Tabs.active(), "ls\r")
Guiltty.Session.dump(Guiltty.Tabs.active()) |> IO.puts()
#+end_src

* One session, three processes

Each tab is one session (the whole tree is in [[file:12-beam-advantage.org][the MVP 4 chapter]]):

#+begin_example
  Session.Supervisor 1    rest_for_one, auto_shutdown: :any_significant
  |-- Pty      (significant)  owns the NIF resource and the shell
  |-- Screen                  owns the grid
  `-- Parser                  owns the parser state
#+end_example

Data flows Pty -> Parser -> Screen:

#+begin_example
  Pty                      Parser                     Screen
   | {:pty_data, bytes}      |                          |
   |------------------------>| feed/2                   |
   |                         | {:apply, commands}       |
   |                         |------------------------->| Terminal.apply/2
   |                         |                          | {:screen_update, ...}
   |                         |                          |-----> subscribers
#+end_example

** What restarts when something crashes
=rest_for_one= restarts the crashed child and every child started *after*
it:

| Crash  | Restarts              | Screen kept? |
|--------+-----------------------+--------------|
| Parser | Parser                | yes          |
| Screen | Screen, Parser        | no           |
| Pty    | Pty, Screen, Parser   | no (new bash)|

A new parser attaches to the Pty in its =init/1=, and the Pty starts
reading again. A test kills the parser mid-session and checks that the
screen keeps its contents and the shell keeps working.

When the Screen restarts, the new one has no subscribers. The Window
monitors the Screen, and when it goes down it subscribes to the new one
(retrying every 50 ms until it exists), so the window keeps updating.

One level up, the root supervisor is =rest_for_one= too:

| Crash             | Restarts                         |
|-------------------+----------------------------------|
| Registry          | Registry, the session, Window    |
| Session.Supervisor| the session, Window              |
| Window            | Window (a new renderer)          |

The Registry comes first because every session process finds the others
through it; if it restarts, all its names are gone, so everything after it
restarts too.

** Killing a supervisor
Killing a supervisor with =Process.exit(pid, :kill)= (or from Observer)
found two bugs on the way, both worth knowing:

#+begin_example
  t=0   session supervisor killed
        |-> root supervisor: "child died, restart it"  -> new Pty wants {:main, :pty}
        `-> old Pty gets an exit signal, but it traps exits,
            so it runs terminate/2 first ... still holding {:main, :pty}
  =>    new Pty: {:error, {:already_started, old_pty}}
        restart fails -> root gives up -> the whole app stops
#+end_example

The fixes:

1. The Pty's =terminate/2= returns immediately and leaves the waiting for
   bash to a helper process, so the old Pty is gone within microseconds.
2. =Guiltty.Session.start_named/3= starts every session process. If the
   name is still held by a process that's on its way out, it waits for that
   process to exit (at most a second) and tries once more. Registry frees a
   name as soon as its owner is no longer alive.

Tests kill the session supervisor and the Screen and check that a working
session comes back and the window follows it.

** When bash exits
The Pty is marked *significant*. When it stops with ={:shutdown, _}= (bash
exited), its =:transient= restart policy says don't restart, and
=auto_shutdown: :any_significant= shuts down the whole session. The session
supervisor's exit tells =Guiltty.Tabs= the tab is gone. In MVP 1 the
session itself was significant, so =exit= closed the window; since MVP 4
only the *last* tab ending stops guiltty, and closing the window stops
nothing but the window.

* Questions

1. Why is a row a binary instead of a list of characters?
2. Why doesn't =:lf= move the cursor to column 0?
3. What's the pending wrap for?
4. Why is the Pty started before the Screen and the Parser?
5. What makes the application stop when you type =exit=?

** Answers
:PROPERTIES:
:VISIBILITY: folded
:END:

1. With ASCII one byte is one cell, a binary is compact, cheap to slice, and
   already the shape the renderer needs.
2. That's what LF means on a terminal. The line discipline's ONLCR turns
   bash's =\n= into =\r\n=, and the =\r= does the column 0 part.
3. So a line exactly as wide as the screen doesn't leave an empty line when
   CR LF follows it.
4. With =rest_for_one=, things started later depend on things started
   earlier. The screen and parser are only meaningful for a given shell, so
   a new Pty must restart them, but not the other way around.
5. Bash exits, the Pty reads EOF and stops with ={:shutdown, _}=. It's
   significant, so its supervisor shuts down, which is significant in the
   application supervisor, which shuts down too.
