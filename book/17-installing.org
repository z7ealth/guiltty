#+TITLE: Installing: the release, the menu entry, the icon
#+STARTUP: overview

* What "installed" means

Running guiltty from the source tree needs Elixir. An installed guiltty
doesn't: it's a Mix *release*, a directory with guiltty's compiled code,
the renderer, the PTY NIF, and a copy of the Erlang runtime (ERTS) itself.
[[file:../install.sh][install.sh]] builds one and puts it, and what a desktop needs to find it,
in your home directory. No root.

#+begin_example
  ~/.local/
  ├── lib/guiltty/                     the release
  │   ├── bin/guiltty                  its start script (and rel/env.sh.eex)
  │   ├── erts-17.1.1/                 its own Erlang
  │   └── lib/guiltty-0.20.1/priv/     guiltty (the client), guiltty_vk, guiltty_gl,
  │                                    pty_nif.so, text_nif.so, guiltty.bmp
  ├── bin/guiltty                      a link to that client (chapter 23)
  └── share/
      ├── applications/guiltty.desktop the menu entry
      └── icons/hicolor/
          ├── 16x16/apps/guiltty.png
          ├── ...
          └── 256x256/apps/guiltty.png
#+end_example

The release is built next to the old one (=lib/guiltty.new=) and swapped
in only when the build worked, so a failed update leaves the installed
guiltty alone. A running installed guiltty is stopped first (after
asking: its tabs close); the one in =_build/prod= is never touched, only
pointed out, because both would use the node name =guiltty@127.0.0.1=.
The swap is two renames (old aside, new in), so there's no moment with
no guiltty installed.

** Updating from inside guiltty

Running =./install.sh= in one of guiltty's own tabs means stopping the
terminal the script runs in. When guiltty stops, the tab's PTY closes,
the kernel sends =SIGHUP= to the tab's foreground job (the script), and
anything it writes to the closed terminal fails. Before v0.16.0 the
script died right there, halfway: after stopping guiltty, before
installing the new one.

Now it notices first. A tab's shell is a child of guiltty's VM, so if
the VM's pid (=bin/guiltty pid=) is among the script's ancestors, it runs
inside. Then it ignores =SIGHUP=, sends the rest of its output to
=~/.local/state/guiltty/install.log=, and at the end opens guiltty again,
on the new version:

#+begin_example
  tab: ./install.sh
    build guiltty.new                 (output in the tab)
    "this tab closes now; ... log: ~/.local/state/guiltty/install.log"
    trap '' HUP; output -> the log
    bin/guiltty stop  ──> every tab closes, this one too: SIGHUP, ignored
    swap, link, menu entry            (output in the log)
    guiltty           ──> a new window, on the new version
#+end_example

Tested on a private X display: the old guiltty stopped, the script
lived on, and a new window of the new version opened about 3 s later.

The installed node listens only on 127.0.0.1, and its cookie (the secret
that lets a program connect to it) comes from =~/.erlang.cookie=, never
from the command line: =install.sh= stops if that file can be read by
anyone but you. Chapter 20 explains why.

* The one-line install

[[file:../get.sh][get.sh]] does the whole of this chapter for someone who has nothing yet:

#+begin_src sh
curl -fsSL https://raw.githubusercontent.com/z7ealth/guiltty/master/get.sh | sh
#+end_src

#+begin_example
  /etc/os-release      ID=opensuse-tumbleweed, ID_LIKE="opensuse suse"
       |                -> family: suse, fedora, debian or arch
       v
  missing packages     asked of the package manager one by one
       |               (rpm -q --whatprovides, dpkg-query, pacman -Q)
       |               -> shows "sudo zypper install ...", asks [y/N]
       v
  Elixir 1.18+ on      if not: says how to get one with asdf, and stops
  OTP 26+?             (one already on the PATH, asdf's say, is used,
       |                and the distribution's isn't added)
       v
  C23 compiler?        a two-line test program with constexpr
       v
  latest tag           api.github.com/repos/z7ealth/guiltty/tags, sorted
       |               by version; GUILTTY_VERSION=v0.18.1 picks one
       v
  source tarball       github.com/.../archive/refs/tags/<tag>.tar.gz
       |               -> ~/.local/src/guiltty-<version> (no git needed)
       v
  install.sh           the rest of this chapter
#+end_example

Two details are about pipes. Run as =curl ... | sh=, the script's stdin is
the script itself, so a question can't be read from it: =ask= reads the
answer from =/dev/tty=, the terminal, directly. And =/dev/tty= can exist
and still fail to open (a container, cron: no controlling terminal), so
=has_tty= tries to open it, and without one only =--yes= goes ahead.

It's POSIX =sh=, not bash: =sh= is what every distribution has where the
pipe lands. =install.sh= stays bash.

Tried: the whole run on a fresh openSUSE Tumbleweed container (packages,
Tumbleweed's own Elixir, the build, the install), and =--dry-run= on
Fedora, Ubuntu 26.04 and Arch, which found every package name.

* What building needs

Building is where Elixir comes in: =install.sh= compiles guiltty, its C
programs and the release on your machine, and checks first that the tools
are there.

| Needed                          | For                                     |
|---------------------------------+-----------------------------------------|
| Elixir 1.18+ on Erlang/OTP 26+ | compiling guiltty and making the release |
| GCC 15 or newer, make, pkg-config | the C: C23 and =#embed= need GCC 15    |
| glslc (shaderc)                 | the Vulkan shaders, GLSL -> SPIR-V       |
| SDL3, FreeType, fontconfig, HarfBuzz, libpng, Vulkan (dev files) | the renderers |

Running the installed copy needs none of the build tools, only the shared
libraries (SDL3, FreeType, fontconfig, HarfBuzz, libpng) and a GPU driver with
OpenGL 3.3. Vulkan is optional: with the loader and a Vulkan 1.3 driver,
guiltty draws with Vulkan; without them, =guiltty_vk= can't start and the
Window falls back to OpenGL by itself (chapter 19). The README has the
commands.

* The menu entry

A =.desktop= file is how every Linux desktop (Xfce, KDE, GNOME) learns an
application exists: a small INI file in =applications/=, under one of the
XDG data directories (=~/.local/share= is yours). The installed one:

#+begin_example
  [Desktop Entry]
  Type=Application
  Name=guiltty
  GenericName=Terminal
  Comment=A GPU terminal emulator in Elixir
  Exec=/home/you/.local/bin/guiltty
  Icon=guiltty
  Terminal=false
  Categories=System;TerminalEmulator;
  StartupWMClass=guiltty
  StartupNotify=false
#+end_example

- =Icon=guiltty= is a name, not a path: the desktop looks it up in the
  icon theme, in the size it needs (16 for a menu, 48 for a launcher).
  That's why there's one PNG per size under =hicolor/=, the fallback
  theme every theme inherits from.
- =Categories= puts it under System, and =TerminalEmulator= tells the
  desktop it's a terminal.
- =StartupNotify=false=: the command returns at once (it asks the running
  guiltty for a window), so a "starting..." cursor would spin for nothing.
- =update-desktop-database= and =gtk-update-icon-cache= refresh the caches
  menus read; =desktop-file-validate= checks the file.

* Which window is whose

When a window appears, how does the taskbar know it belongs to
guiltty.desktop? On X11, by the window's *class*, =WM_CLASS=, matched
against =StartupWMClass=. The renderer calls =SDL_SetAppMetadata= before
=SDL_Init=, and SDL sets the class from it (on Wayland, the =app_id=). From
=xprop= on the installed guiltty's window:

#+begin_example
  WM_CLASS(STRING) = "guiltty_vk", "guiltty"
                      instance      class: matches StartupWMClass
  _NET_WM_ICON(CARDINAL) = Icon (128 x 128): ...
#+end_example

Some taskbars (Xfce's among them) take the icon from the window itself,
=_NET_WM_ICON=, not from the .desktop file. So the renderer sets one too,
with =SDL_SetWindowIcon=. SDL3 reads only BMP images, so the logo also
lives as =priv/guiltty.bmp=, which the renderer finds next to itself
(=SDL_GetBasePath=).

* The icons, from the logo

The logo is an SVG: the guiltty mark (a cursor bar, =>= and =_=) on a dark
rounded card, =priv/icons/logo.svg=. =make icons= ([[file:../c_src/tools/icons.sh][icons.sh]]) renders it
into every size, and ImageMagick makes the BMP.

Small sizes are their own design problem. At 16 pixels the gap between
the cursor bar and the chevron is under a pixel, and they melt into one
shape that reads like =D_=. So, as icon sets usually do, the two smallest
sizes come from a simpler drawing, =logo-small.svg=: just =>_=, with
slightly bolder strokes.

#+begin_example
  logo.svg        ->  32, 48, 64, 128, 256 px, and guiltty.bmp (128)
  logo-small.svg  ->  16, 24 px
#+end_example

ImageMagick on openSUSE won't read SVG (its security policy forbids it),
so the script renders with =rsvg-convert= when it's installed and with
headless Chromium otherwise.

* Loot

- The freedesktop.org Desktop Entry Specification (keys like =Exec=,
  =Categories=, =StartupWMClass=) and the Icon Theme Specification
  (=hicolor=, the sizes, the lookup).
- XDG Base Directory Specification: =~/.local/share=, =~/.config=.
- ICCCM, =WM_CLASS=; EWMH, =_NET_WM_ICON=. =xprop(1)= shows both.
- Mix releases: =mix release --path=, =include_erts=.
- =desktop-file-validate(1)=, =update-desktop-database(1)=.
- =credentials(7)= and =termios(3)=: a terminal's hangup sends =SIGHUP= to
  its foreground job; =signal(7)=: an ignored signal stays ignored across
  =fork= and =exec=; =proc_pid_stat(5)=: the parent pid.
- =os-release(5)=: =ID= and =ID_LIKE=; =tty(4)=: =/dev/tty=, the
  controlling terminal; =sh(1p)= (POSIX shell) for what =get.sh= may use.

* Questions

1. Why does the installed guiltty run on a machine without Elixir?
2. Why is =Icon= a name and not a path, and why one PNG per size?
3. How does the taskbar know a window belongs to guiltty.desktop?
4. Why does guiltty need a BMP copy of its logo?
5. Why did updating from inside guiltty stop halfway, and how does the
   script tell it's running inside guiltty?
6. Piped into =sh=, how does =get.sh= ask you anything, and why isn't
   checking that =/dev/tty= is readable enough?

** Answers
:PROPERTIES:
:VISIBILITY: folded
:END:

1. The release carries its own Erlang runtime (ERTS) and guiltty's
   compiled code; nothing else from Elixir is needed to run it.
2. The desktop looks the name up in the icon theme and picks the size it
   needs; a theme can also replace it. Scaling one big PNG down on the fly
   looks worse.
3. By the window's class, =WM_CLASS= (=app_id= on Wayland), which the
   renderer sets to =guiltty= and the entry's =StartupWMClass= names.
4. Some taskbars take the icon from the window (=_NET_WM_ICON=), and SDL3
   can only load BMP files to set it.
5. Stopping guiltty closes the tab the script runs in: the kernel sends
   it =SIGHUP=, which kills a script by default. It now walks its parent
   pids (=/proc/<pid>/stat=) looking for guiltty's VM; if it's there, it
   ignores =SIGHUP= and writes to a log instead of the closed terminal.
6. Its stdin is the script, coming down the pipe; it reads answers from
   =/dev/tty=, the controlling terminal, instead. In a container or cron
   there is none: the file exists but opening it fails, so it tries to
   open it.
