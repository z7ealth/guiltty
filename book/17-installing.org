#+TITLE: Installing: the release, the menu entry, the icon
#+STARTUP: overview

* What "installed" means

Running guiltty from the source tree needs Elixir. An installed guiltty
doesn't: it's a Mix *release*, a directory with guiltty's compiled code,
the renderer, the PTY NIF, and a copy of the Erlang runtime (ERTS) itself.
[[file:../install.sh][install.sh]] gets one (downloaded, or built from source) and puts it,
and what a desktop needs to find it, in your home directory. No root.

#+begin_example
  ~/.local/
  ├── lib/guiltty/                     the release
  │   ├── bin/guiltty                  its start script (and rel/env.sh.eex)
  │   ├── erts-17.1.1/                 its own Erlang
  │   └── lib/guiltty-0.26.0/priv/     guiltty (the client), guiltty_vk, guiltty_gl,
  │                                    pty_nif.so, text_nif.so, guiltty.bmp
  ├── bin/guiltty                      a link to that client (chapter 23)
  └── share/
      ├── applications/guiltty.desktop the menu entry
      └── icons/hicolor/
          ├── 16x16/apps/guiltty.png
          ├── ...
          └── 256x256/apps/guiltty.png
#+end_example

The new release is put next to the old one (=lib/guiltty.new=) and
swapped in only when that worked, so a failed update leaves the
installed guiltty alone. A running installed guiltty is stopped first (after
asking: its tabs close); the one in =_build/prod= is never touched, only
pointed out, because both would use the node name =guiltty@127.0.0.1=.
The swap is two renames (old aside, new in), so there's no moment with
no guiltty installed.

** Updating from inside guiltty

Running =./install.sh= in one of guiltty's own tabs means stopping the
terminal the script runs in. When guiltty stops, the tab's PTY closes,
the kernel sends =SIGHUP= to the tab's foreground job (the script), and
anything it writes to the closed terminal fails. Before v0.16.0 the
script died right there, halfway: after stopping guiltty, before
installing the new one.

Now it notices first. A tab's shell is a child of guiltty's VM, so if
the VM's pid (=bin/guiltty pid=) is among the script's ancestors, it runs
inside. Then it ignores =SIGHUP=, sends the rest of its output to
=~/.local/state/guiltty/install.log=, and at the end opens guiltty again,
on the new version:

#+begin_example
  tab: ./install.sh
    build guiltty.new                 (output in the tab)
    "this tab closes now; ... log: ~/.local/state/guiltty/install.log"
    trap '' HUP; output -> the log
    bin/guiltty stop  ──> every tab closes, this one too: SIGHUP, ignored
    swap, link, menu entry            (output in the log)
    guiltty           ──> a new window, on the new version
#+end_example

Tested on a private X display: the old guiltty stopped, the script
lived on, and a new window of the new version opened about 3 s later.

The installed node listens only on 127.0.0.1, and its cookie (the secret
that lets a program connect to it) comes from =~/.erlang.cookie=, never
from the command line: =install.sh= stops if that file can be read by
anyone but you. Chapter 20 explains why.

* One install.sh, three ways in

Until v0.26.0 there were two scripts: =get.sh=, piped from curl, which
installed build packages and downloaded the source, and =install.sh=,
which built it. On a fresh Fedora, Ubuntu and Arch, that never got as
far as a running guiltty (the next section says why). Now there's one
[[file:../install.sh][install.sh]], and where it finds itself decides what it does:

#+begin_example
  curl ... | bash             BASH_SOURCE is empty: there's no file
        |                     -> download the latest release (below)
        v
  ./install.sh, next to a     an unpacked release tarball
  release/ directory          -> install that release
        |
  ./install.sh, next to       a git checkout
  mix.exs                     -> build from source (mix release)
        |
        v
  check glibc and the libraries (not for a source build: it has them, or
        |               the build fails)
        |               -> glibc too old: say so, stop, install nothing
        |               -> missing ones: "sudo apt install ...", [y/N]
        v
  stop the installed guiltty (asks), swap the release in, link the
  command, menu entry and icons
#+end_example

Downloading:

#+begin_example
  latest tag     api.github.com/repos/z7ealth/guiltty/releases/latest
       |         (GUILTTY_VERSION=v0.26.0 picks one instead)
       v
  tarball        github.com/z7ealth/guiltty/releases/download/v0.26.0/
       |           guiltty-0.26.0-x86_64-linux.tar.gz   and its .sha256
       v
  sha256sum -c   a damaged download stops here
       v
  unpacked into a temporary directory, removed at the end
#+end_example

The checksum only catches a broken download: anyone who could swap the
tarball could swap the checksum next to it. What protects you is HTTPS
from github.com, which is why the script is worth reading before piping it.

Three details are about pipes:

- *The whole script is read first.* Bash reads a script from a pipe a
  line at a time, so a command that reads stdin could swallow the rest of
  the script. Everything is in functions, and the last line calls =main=:
  bash has to read to the end before anything runs.
- *Questions go to the terminal.* stdin is the script, so =ask= reads the
  answer from =/dev/tty=. =/dev/tty= can exist and still fail to open (a
  container, cron: no controlling terminal), so =has_tty= tries to open
  it, and without one only =--yes= goes ahead.
- *bash, not sh.* The one-liner says =| bash=: install.sh uses arrays and
  =<<<=, and bash is on every distribution's desktop.

** Which libraries are missing

The release carries guiltty, its Erlang and SDL3. The rest it takes from
the system, and =ldd= says which of those can't be found:

#+begin_example
  $ ldd guiltty_vk           (on a bare Ubuntu 24.04 container)
      libfontconfig.so.1 => not found
      libharfbuzz.so.0 => not found
      libfreetype.so.6 => not found
      libpng16.so.16 => not found
      libvulkan.so.1 => not found
      libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6
#+end_example

install.sh reads =/etc/os-release= (=ID=, =ID_LIKE=) to learn the
family (openSUSE, Fedora, Debian/Ubuntu, Arch), turns each missing
library into that family's package name (=package_for=), shows the
command and asks:

#+begin_example
  guiltty needs these libraries, and this system doesn't have them: libfontconfig.so.1 ...
    sudo apt update && sudo apt install libfontconfig1 libfreetype6 libharfbuzz0b libpng16-16 libvulkan1
  Install them now? [y/N]
#+end_example

It checks every binary of guiltty's own: the two renderers, the
client, both NIFs and the VM. The NIFs matter as much as the renderers:
they're loaded into the VM only when a tab opens, so one that can't load
fails late, with the window already up.

** A glibc too old

One library can't be fixed by installing a package: the C library
itself, glibc, which is the distribution's own. If it's older than the
release needs, =ldd= says so in a line of its own:

#+begin_example
  $ ldd pty_nif.so           (on Ubuntu 22.04, glibc 2.35)
  pty_nif.so: /lib/x86_64-linux-gnu/libc.so.6: version `GLIBC_2.36' not found
      (required by pty_nif.so)
#+end_example

install.sh picks out the newest version asked for, asks glibc for its own
(=getconf GNU_LIBC_VERSION=) and stops before installing anything:

#+begin_example
  guiltty: this guiltty needs glibc 2.36 or newer, and this system has 2.35.
  guiltty: That's Ubuntu 24.04 or 26.04, Debian 12, or any current Fedora, Arch or openSUSE;
  guiltty: on an older system, build from source instead (README, "Build from source")
#+end_example

The first version of this message said "this system has ?". It got the
number from =ldd --version | head -n 1=: =head= exits after one line,
=ldd= is killed by =SIGPIPE= writing the rest, and under =set -o pipefail=
that failed pipeline was taken as "couldn't tell". =getconf= gives the
answer with no pipe to break. Until v0.26.1 there was no check at all:
on Ubuntu 22.04 everything installed, and then the PTY NIF refused to
load when guiltty opened its first tab.

** Missing Vulkan

Vulkan alone is optional (guiltty falls back to OpenGL, chapter 19), so
a missing Vulkan loader is never mentioned on its own. It only joins the
install command when something else is missing too. The parsing is plain
bash, with no awk: a minimal openSUSE image has no awk. The first version
used it, and on such a system the check failed without a word and the
install went ahead without the libraries. A check that can't run has to
stop the script, not pass.

On Arch the command is =pacman -Syu --needed=, not =pacman -S=. Arch
supports only whole-system upgrades: installing a package from a fresh
package list onto an older system can pull in a library newer than the
ones installed (a "partial upgrade") and break them. In testing, a fresh
Arch container installing curl that way got an OpenSSL 4 that pacman
itself couldn't use.

** By hand

The README has two ways without the pipe. One downloads the tarball,
checks it (=sha256sum -c=) and runs the =install.sh= inside it: the same
script, which finds =release/= next to itself. The other does without
any script. That's a list of commands, because all install.sh does
is in this chapter: libraries, then the release in =~/.local/lib/guiltty=,
the link, the icons and the =.desktop= file.

The one step that isn't obvious is the link. =~/.local/bin/guiltty= must
be a symbolic link into the release, not a copy of the client. The client
finds the release it belongs to by following its own path
(=/proc/self/exe=, chapter 23), so a copy elsewhere wouldn't know which
release to start.

* What building needs

Building is where Elixir comes in. Run in a git checkout, =install.sh=
compiles guiltty, its C programs and the release on your machine, and
checks first that the tools are there. If some are missing, it lists
them and points to the one-line install instead.

| Needed                          | For                                     |
|---------------------------------+-----------------------------------------|
| Elixir 1.18+ on Erlang/OTP 26+ | compiling guiltty and making the release |
| GCC 15 or newer, make, pkg-config | the C: C23 and =#embed= need GCC 15    |
| glslc (shaderc)                 | the Vulkan shaders, GLSL -> SPIR-V       |
| SDL3, FreeType, fontconfig, HarfBuzz, libpng, Vulkan (dev files) | the renderers |

Running the installed copy needs none of the build tools, only the shared
libraries (FreeType, fontconfig, HarfBuzz, libpng, and SDL3 when built
from source) and a GPU driver with
OpenGL 3.3. Vulkan is optional: with the loader and a Vulkan 1.3 driver,
guiltty draws with Vulkan; without them, =guiltty_vk= can't start and the
Window falls back to OpenGL by itself (chapter 19). The README has the
commands.

* The precompiled release

Building needs newer tools than many distributions ship. Ubuntu 24.04 has
GCC 13, which can't compile =#embed=, Elixir 1.14 and no SDL3 package at all.
So =make dist= builds the release once, in a container, and packs it as
=_build/dist/guiltty-<version>-x86_64-linux.tar.gz= (about 10 MB).

** Why it runs elsewhere: glibc only goes forward

A program records the glibc symbol *versions* it was linked against
(=memcpy@GLIBC_2.14=). The loader refuses to run it where glibc is older,
and newer glibcs keep every old version. So the rule is: build on the
oldest glibc you want to support. [[file:../dist/Dockerfile][dist/Dockerfile]] builds on Debian 12
(glibc 2.36), which covers Debian 12, the Ubuntu LTS releases guiltty
supports (24.04 and 26.04), and every current Fedora, Arch and openSUSE.

Building on 2.36 doesn't by itself mean needing 2.36: a binary asks only
for the versions of the functions it calls. Most of guiltty would run on
2.34. The PTY NIF is what needs 2.36, because it calls =pidfd_open= and
=pidfd_send_signal= (chapter 2), whose wrappers glibc added in 2.36.
=objdump -T= shows it:

#+begin_example
  $ objdump -T priv/pty_nif.so | grep GLIBC_2.36
  0000000000000000      DF *UND*  0000000000000000 (GLIBC_2.36) pidfd_send_signal
  0000000000000000      DF *UND*  0000000000000000 (GLIBC_2.36) pidfd_open
#+end_example

#+begin_example
  debian:bookworm (glibc 2.36)
    ├── Erlang/OTP 29.1.2, built from source   (cached: built once)
    ├── Elixir 1.20.5, precompiled
    ├── Clang 20 (apt.llvm.org)                C23 and #embed
    ├── SDL 3.4.18, built as a static library
    └── dist/build.sh
          GUILTTY_DIST=1 mix release           Makefile: SDL linked in,
          strip, check NEEDED, tar             no -dbg renderers
#+end_example

** What it may need from your machine

Every file says which shared libraries it needs (=NEEDED= in its dynamic
section, =readelf -d=). [[file:../dist/build.sh][dist/build.sh]] fails the build if any binary
needs something outside this list:

| Who                         | May need                                                 |
|-----------------------------+----------------------------------------------------------|
| the renderers               | libc, libm, fontconfig, FreeType, HarfBuzz, libpng, Vulkan |
| the NIFs and the client     | libc                                                     |
| the Erlang runtime (ERTS)   | libc, libm, libstdc++, libgcc_s, zlib                    |

Two libraries are deliberately absent:

- *SDL3* is linked in statically. SDL then loads X11, Wayland, EGL,
  PulseAudio, IBus and the rest with =dlopen= when it starts, choosing
  whatever the machine has, so a system without PipeWire, say, still runs.
- *libtinfo* (ncurses, used by the Erlang shell) is linked into the
  Erlang runtime. The first attempt used a prebuilt Erlang that linked it
  dynamically, and on openSUSE Tumbleweed the VM didn't start:

#+begin_example
  beam.smp: symbol lookup error: beam.smp: undefined symbol: strfnames,
  version NCURSES6_TINFO_5.0.19991023
#+end_example

  Debian builds libtinfo with symbol versions and openSUSE doesn't, and
  Fedora printed a warning about it on every command. So the Dockerfile
  builds Erlang itself. It deletes the =libtinfo.so= development link
  first, which leaves the linker only =libtinfo.a= to use.

** Licenses

Shipping other people's code means shipping their licenses. The
Dockerfile keeps a copy of each as it builds, and the tarball carries
them in =licenses/=: Erlang and Elixir (Apache 2.0, with parts of Erlang
under BSD and MIT), SDL3 (zlib), ncurses (MIT-style: its notice must go
with every copy) and telemetry (Apache 2.0).

** Publishing it: the release workflow

[[file:../.github/workflows/release.yml][.github/workflows/release.yml]] runs when a tag like =v0.26.0= is pushed:

#+begin_example
  git push origin v0.26.0
       |
       v
  GitHub Actions (ubuntu-24.04 runner)
    1. the tag must match mix.exs's version   else the tarball's name
                                              wouldn't match what
                                              install.sh asks for
    2. make dist                              ~10 min: Erlang and SDL
                                              from source, no cache
    3. make dist-check                        five distributions, and one
                                              too old (must be refused)
    4. gh release create v0.26.0              tarball + .sha256, notes
                                              = CHANGELOG's 0.26.0 section
#+end_example

Step 3 is why it can't publish a broken tarball: [[file:../dist/smoke.sh][dist/smoke.sh]] starts a
bare container of each distribution, adds only what a desktop always has
(Mesa and a font), and runs =install.sh --yes= from the unpacked tarball.
Then =guiltty version= has to answer, both NIFs have to load, and both
renderers have to draw the replay fixture offscreen. The workflow's token
may write the repository's contents (=permissions: contents: write=),
which is what creating a release needs, and nothing else.

The check ends with Ubuntu 22.04, which is too old (glibc 2.35). There
install.sh must say "needs glibc" and leave nothing installed, and the
check fails if it doesn't.

A tag push doesn't always start a run: for v0.26.0 none appeared until
the tag was deleted on GitHub and pushed again. So the workflow can also
be started by hand (=workflow_dispatch=): in the Actions tab, "release",
"Run workflow", with the tag picked under "Use workflow from". Started
from a branch instead, it stops at its first step, because "master"
isn't the version in =mix.exs=.

** Tried

The tarball was unpacked in fresh containers of Ubuntu 24.04, Debian 12,
Fedora, Arch and openSUSE Tumbleweed, with only the runtime libraries
installed: ERTS started and loaded both NIFs, and both renderers replayed
=test/fixtures/replay/session.msgs= offscreen on Mesa's software drivers
and saved a screenshot. On Debian 12 only the OpenGL replay ran, because
its lavapipe has no =VK_EXT_headless_surface= (a limit of the headless
test, not of a desktop).

Then the whole install, in bare containers of the same five
(=make dist-check=, and by hand for the paths it doesn't take): from an
unpacked tarball with =--yes=, installing the missing libraries first;
=--uninstall= and a download, both piped into bash, with the download
served from a local file; a damaged download (refused: checksum
mismatch); no terminal and no =--yes= (shows the command, stops); and a
checkout with no build tools (lists them, points to the one-liner).

The workflow published v0.26.0 in about 15 minutes, and the one-liner,
run in a fresh Ubuntu 24.04 container, downloaded that release from
GitHub and installed it. Not tried yet: a real desktop on each
distribution.

* The menu entry

A =.desktop= file is how every Linux desktop (Xfce, KDE, GNOME) learns an
application exists: a small INI file in =applications/=, under one of the
XDG data directories (=~/.local/share= is yours). The installed one:

#+begin_example
  [Desktop Entry]
  Type=Application
  Name=guiltty
  GenericName=Terminal
  Comment=A GPU terminal emulator in Elixir
  Exec=/home/you/.local/bin/guiltty
  Icon=guiltty
  Terminal=false
  Categories=System;TerminalEmulator;
  StartupWMClass=guiltty
  StartupNotify=false
#+end_example

- =Icon=guiltty= is a name, not a path: the desktop looks it up in the
  icon theme, in the size it needs (16 for a menu, 48 for a launcher).
  That's why there's one PNG per size under =hicolor/=, the fallback
  theme every theme inherits from.
- =Categories= puts it under System, and =TerminalEmulator= tells the
  desktop it's a terminal.
- =StartupNotify=false=: the command returns at once (it asks the running
  guiltty for a window), so a "starting..." cursor would spin for nothing.
- =update-desktop-database= and =gtk-update-icon-cache= refresh the caches
  menus read; =desktop-file-validate= checks the file.

* Which window is whose

When a window appears, how does the taskbar know it belongs to
guiltty.desktop? On X11, by the window's *class*, =WM_CLASS=, matched
against =StartupWMClass=. The renderer calls =SDL_SetAppMetadata= before
=SDL_Init=, and SDL sets the class from it (on Wayland, the =app_id=). From
=xprop= on the installed guiltty's window:

#+begin_example
  WM_CLASS(STRING) = "guiltty_vk", "guiltty"
                      instance      class: matches StartupWMClass
  _NET_WM_ICON(CARDINAL) = Icon (128 x 128): ...
#+end_example

Some taskbars (Xfce's among them) take the icon from the window itself,
=_NET_WM_ICON=, not from the .desktop file. So the renderer sets one too,
with =SDL_SetWindowIcon=. SDL3 reads only BMP images, so the logo also
lives as =priv/guiltty.bmp=, which the renderer finds next to itself
(=SDL_GetBasePath=).

* The icons, from the logo

The logo is an SVG: the guiltty mark (a cursor bar, =>= and =_=) on a dark
rounded card, =priv/icons/logo.svg=. =make icons= ([[file:../c_src/tools/icons.sh][icons.sh]]) renders it
into every size, and ImageMagick makes the BMP.

Small sizes are their own design problem. At 16 pixels the gap between
the cursor bar and the chevron is under a pixel, and they melt into one
shape that reads like =D_=. So, as icon sets usually do, the two smallest
sizes come from a simpler drawing, =logo-small.svg=: just =>_=, with
slightly bolder strokes.

#+begin_example
  logo.svg        ->  32, 48, 64, 128, 256 px, and guiltty.bmp (128)
  logo-small.svg  ->  16, 24 px
#+end_example

ImageMagick on openSUSE won't read SVG (its security policy forbids it),
so the script renders with =rsvg-convert= when it's installed and with
headless Chromium otherwise.

* Questions

1. Why does the installed guiltty run on a machine without Elixir?
2. Why is =Icon= a name and not a path, and why one PNG per size?
3. How does the taskbar know a window belongs to guiltty.desktop?
4. Why does guiltty need a BMP copy of its logo?
5. Why did updating from inside guiltty stop halfway, and how does the
   script tell it's running inside guiltty?
6. Piped into bash, how does =install.sh= ask you anything, and why
   does it put everything in functions and call =main= on the last line?
7. Why is the precompiled release built on Debian 12, not on the newest
   distribution, and why is SDL3 linked in while FreeType isn't?
8. How does install.sh find out which libraries are missing, and what
   went wrong the first time on a minimal openSUSE?
9. The release is built on glibc 2.36, but most of it would run on 2.34.
   What makes 2.36 the real floor, and how does install.sh find out
   before installing anything?

** Answers
:PROPERTIES:
:VISIBILITY: folded
:END:

1. The release carries its own Erlang runtime (ERTS) and guiltty's
   compiled code; nothing else from Elixir is needed to run it.
2. The desktop looks the name up in the icon theme and picks the size it
   needs; a theme can also replace it. Scaling one big PNG down on the fly
   looks worse.
3. By the window's class, =WM_CLASS= (=app_id= on Wayland), which the
   renderer sets to =guiltty= and the entry's =StartupWMClass= names.
4. Some taskbars take the icon from the window (=_NET_WM_ICON=), and SDL3
   can only load BMP files to set it.
5. Stopping guiltty closes the tab the script runs in: the kernel sends
   it =SIGHUP=, which kills a script by default. It now walks its parent
   pids (=/proc/<pid>/stat=) looking for guiltty's VM; if it's there, it
   ignores =SIGHUP= and writes to a log instead of the closed terminal.
6. Its stdin is the script, coming down the pipe; it reads answers from
   =/dev/tty=, the controlling terminal, instead (in a container or cron
   there is none: the file exists but opening it fails, so it tries to
   open it). Bash reads a piped script a line at a time, so a command
   that reads stdin could eat the rest of it; with everything in
   functions, bash must read to the last line before anything runs.
7. A binary runs only on a glibc at least as new as the one it was built
   against, so building on an older one covers more systems. SDL3 isn't
   packaged everywhere (Ubuntu 24.04 has none), while FreeType,
   fontconfig, HarfBuzz and libpng are on every desktop and get security
   updates from the distribution.
8. It runs =ldd= on every binary (renderers, client, NIFs, =beam.smp=) and collects the
   lines that say =not found=, then maps each library to the family's
   package name. The first version filtered with awk, which that image
   didn't have: the filter printed nothing, so nothing looked missing, and
   the install went ahead without the libraries.
9. The PTY NIF calls =pidfd_open= and =pidfd_send_signal=, whose glibc
   wrappers are versioned =GLIBC_2.36=. On an older glibc, =ldd= on the
   NIF prints "version `GLIBC_2.36' not found"; install.sh looks for
   that line in every binary's =ldd= output and stops with the version
   it found (=getconf GNU_LIBC_VERSION=).
