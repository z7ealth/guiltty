#+TITLE: The BEAM advantage: tabs, crashes, detaching, live config
#+STARTUP: overview

* What changes in MVP 4

Until now guiltty was "a window with a shell in it". In MVP 4 the shells
become the long-lived part, and the window becomes a view on them. Since
v0.13.0 there can be many windows, each a *desk* with its own tabs
(chapter 21 tells that story):

#+begin_example
  Guiltty.Supervisor (rest_for_one)
  |-- Guiltty.Registry          sessions by {tab id, role}, desks by {:desk, id}
  |-- Guiltty.Config            ~/.config/guiltty/config.exs, reloaded on save
  |-- Guiltty.Sessions          DynamicSupervisor: every tab of every window
  |   |-- Session.Supervisor    (rest_for_one: Pty, Screen, Parser)
  |   `-- ...
  |-- Guiltty.Desks             DynamicSupervisor: one Desk per window
  |   |-- Desk 1                (rest_for_one, auto_shutdown)
  |   |   |-- Guiltty.Tabs      its tabs: order, active, locked   (significant)
  |   |   `-- Guiltty.Window    its renderer port
  |   `-- Desk 2 ...
  |-- Guiltty.Lifeline          watches the desks                 (significant)
  `-- (a Task)                  opens the first window at boot
#+end_example

- *Tabs* ([[file:../lib/guiltty/tabs.ex][Guiltty.Tabs]]) are sessions, started under a DynamicSupervisor
  with ids unique across all windows. A tab ends when its shell exits.
  When a desk's last tab ends, its =Tabs= stops; it's /significant/ in
  its desk, so the desk stops.
- *The window is not significant.* Closing it stops the Window and its
  renderer. The Window first closes every tab of its desk that isn't
  *locked* (Ctrl+Shift+L). With none locked, the last tab ending ends the
  desk; locked tabs keep it running.
- *Lifeline* ([[file:../lib/guiltty/lifeline.ex][Guiltty.Lifeline]]) watches the desks. When the last one
  ends, it stops; it's significant, so guiltty stops.

* What survives a crash, part by part

Every Elixir part can crash and come back without taking the rest. Two
things can't: the NIFs (the PTY's and the text's) run inside the BEAM,
so a crash in either stops the whole VM, and so does the VM itself
running out of memory. Then every tab goes (chapter 20 is how the NIFs
are kept from crashing).

The second one has a guard. Each session's processes run with a heap limit
(=max_heap_size=, 2 GB): a tab that goes past it is killed by the BEAM and
restarted, and the other tabs never hear about it. From OTP 27 the limit counts
large binaries too, which is what a tab's rows and images are; on OTP 26 only the
heap, so those have limits of their own.

| What crashes            | What restarts                          | What you see                       |
|-------------------------+----------------------------------------+------------------------------------|
| a Parser                | that Parser                            | the halo; the screen stays         |
| a Screen or a Pty       | that tab's session processes           | the window follows the new Screen  |
| a Session.Supervisor    | that tab, same id                      | the tab stays in place             |
| the renderer (kill -9)  | that desk's Window, which starts a renderer | the window comes back, all tabs |
| a desk's Tabs           | that Tabs, and its Window; the Tabs finds its sessions | nothing: the tabs are taken back |
| a whole Desk            | that desk, same id                     | that window comes back; others never notice |

** Killing a parser
To watch a parser crash and come back, kill it from =guiltty remote= (or
Observer), with vim open in the active tab:

#+begin_src elixir
[desk | _] = Guiltty.Desk.all()
Process.exit(GenServer.whereis(Guiltty.Session.via(Guiltty.Tabs.active(Guiltty.Desk.tabs(desk)), :parser)), :kill)
#+end_src

#+begin_example
  Process.exit(parser, :kill)
  Session.Supervisor (rest_for_one): Parser is last, so only it restarts
  new Parser: Pty.attach_parser
  Pty: "a parser again?"  -> telemetry [:guiltty, :session, :parser_restarted]
                          -> SIGWINCH to the foreground job (winch/1 NIF)
  Window (telemetry handler): HALO -> the window's border flashes blue
  vim (SIGWINCH): redraws everything, repairing whatever bytes were lost
#+end_example

The bytes the old parser had in hand are gone. That's why the Pty sends
SIGWINCH: full-screen programs redraw on it, so the screen heals itself.

** Taking the tabs back
If a desk's =Tabs= crashes, its sessions keep running (they're under
=Guiltty.Sessions=, not under =Tabs=). Each session's supervisor is
registered with its desk's id as the Registry /value/, so the new =Tabs=
asks for the ={id, :supervisor}= keys whose value is its desk, and adopts
those: another window's tabs stay where they are.

** Keeping the layout: an ETS table with an heir

Taking the sessions back used to be all: each came back as a tab of its
own, and the splits, names, locks and marks died with the old =Tabs=. Now
they're kept in an ETS table, and the table outlives the process.

An ETS table belongs to the process that created it, and is deleted when
that process dies. Unless the table names an /heir/: then the BEAM gives
it to the heir instead, with an ='ETS-TRANSFER'= message. Each desk has
a tiny =Guiltty.Tabs.Keeper= for that job
([[file:../lib/guiltty/tabs/keeper.ex][keeper.ex]]):

#+begin_example
  Desk (rest_for_one)
  ├── Keeper    creates the table (heir: itself), gives it to Tabs
  ├── Tabs      owns it; on every change, :ets.insert(table, {:saved, layout})
  └── Window

  Tabs crashes
    BEAM:    the table's owner died, it has an heir -> Keeper owns it now
    Supervisor: starts a new Tabs (and, rest_for_one, a new Window)
    new Tabs:   Keeper.take(keeper) -> :ets.give_away(table, new_tabs, :taken)
                reads {:saved, layout}, keeps the panes whose sessions are alive
#+end_example

Why a table and not the Keeper's own state? Writing is a local
=:ets.insert/2= in =Tabs=: no message, no waiting on another process. The
table is =:protected=, so only its owner can write it, and the Keeper
holds it only in between. There's one race worth knowing: the supervisor
can start the new =Tabs= before the transfer message reaches the Keeper,
so =take/1= waits up to a second for it (=await_owner/1=).

The broadcast group isn't kept on purpose. Joining checks what each pane
is running (chapter 18); after a crash you join again, rather than have
your keystrokes fan out to servers without having asked.

* Idle tabs give memory back

A process's heap grows to hold its busiest moment, and stays that size
until it's collected. A tab that ran a build and has been idle since keeps
that heap. =Screen= and =Parser= start with =hibernate_after: 5_000=: after
five seconds with no message, =gen_server= hibernates the process, which
does a full garbage collection and shrinks the heap to what's live. The
next message wakes it, at the cost of one more collection.

Measured on a tab that printed 300,000 lines and then sat idle
(=Process.info(pid, [:memory, :binary])=):

| process | heap after the flood | after 8 s idle |
|---------+----------------------+----------------|
| Screen  | 161 KB               | 39 KB          |
| Parser  | 278 KB               | 1 KB           |

The rows themselves (1.5 MB of scrollback, as refcounted binaries) don't
move: they're live. Two other flags were tried and left out, because
measuring showed nothing to fix: =fullsweep_after= (no dead row binaries
were piling up) and =message_queue_data: :off_heap= (backpressure keeps
each queue at one chunk, so there's no long queue to move off the heap).

* The watchdog

=Guiltty.Watchdog= ([[file:../lib/guiltty/watchdog.ex][watchdog.ex]]) asks the BEAM, with
=:erlang.system_monitor/2=, to report any process whose garbage
collection takes over 100 ms (a tab that stutters) or whose heap passes
256 MB (a tab heading for the 2 GB limit). It logs a warning naming the
process by its Registry key, ={7, :screen}= for tab 7's screen, at most
once a minute per process, and sends the same as telemetry. A node has
only one system monitor: if you attach =recon= or another tool that sets
one, the watchdog goes quiet.

* Looking inside a running guiltty

The guiltty you use every day is a node, =guiltty@127.0.0.1=, and any
Erlang node that has your cookie (=~/.erlang.cookie=) and runs on this
machine can connect to it (chapter 20). =guiltty remote= is one such node,
with an iex shell. Observer is another, with windows.

Observer runs in your own Erlang, not in guiltty: it needs =wx= (21 MB),
and guiltty has no use for it. But to show a remote node, Observer calls
=observer_backend= on that node, and that module is in =runtime_tools=.
So the release carries =runtime_tools=, loaded and never started
([[file:../mix.exs::runtime_tools: :load][mix.exs]]): 740 KB of code that waits for a tool to call it.

#+begin_example
  your Erlang (any, OTP 26+)              guiltty@127.0.0.1 (the release)
  +--------------------------+            +-----------------------------+
  | observer@127.0.0.1       |  cookie,   | runtime_tools (loaded):     |
  | -hidden                  |  127.0.0.1 |   observer_backend  <-- rpc |
  | observer, wx (windows)   | ---------> |   dbg, msacc                |
  +--------------------------+            | guiltty, its tabs ...       |
                                          +-----------------------------+
#+end_example

#+begin_src sh
  erl -hidden -name observer@127.0.0.1 -noshell \
      -eval "observer:start_and_wait('guiltty@127.0.0.1'), halt()."
#+end_src

=-hidden= keeps the connection out of =nodes()=, so guiltty doesn't see a
new peer, only a visitor; =start_and_wait= returns when you close the
window, and =halt()= then ends that Erlang. Against v0.24.0, which didn't
carry =runtime_tools=, the System tab crashes at once: ={active,
'guiltty@127.0.0.1'}= in the error is Observer asking a node that can't
answer.

What to look at:

- *Processes*, sorted by Memory: one =Screen= and one =Parser= per pane.
  Leave a tab idle and watch both shrink after five seconds (hibernation,
  above).
- *Applications*: the supervision tree of chapter 8, live.
- *Load Charts*: memory over time. During =bench/soak.exs= it should
  level off.
- *Table Viewer*: the Keeper's ETS table.

The same module set works from =guiltty remote=. =:dbg= traces calls and
messages; =:msacc= says where the schedulers spend their time:

#+begin_src elixir
  :dbg.tracer()
  :dbg.p(:all, :c)
  :dbg.tp(Guiltty.Window.Protocol, :attention, 0, [])
  # a long command ends while you're in another window:
  # (<0.512.0>) call 'Elixir.Guiltty.Window.Protocol':attention()
  :dbg.stop()                # a forgotten trace slows guiltty down

  :msacc.start(5_000)        # while a tab runs `cat` on a big file
  :msacc.print()             # per scheduler: emulator, gc, nif, port, sleep
#+end_src

And plain memory questions need nothing extra:

#+begin_src elixir
  :erlang.memory()           # total, processes, binary, ets
  Process.list()
  |> Enum.map(&{&1, Process.info(&1, [:memory, :registered_name])})
  |> Enum.sort_by(fn {_, i} -> -i[:memory] end)
  |> Enum.take(10)
#+end_src

Carrying =runtime_tools= opens nothing new: anyone who can connect could
already run any code in guiltty through =guiltty remote=.

* Detach and reattach

This is per tab: lock the ones you want to keep with Ctrl+Shift+L (they
show a 🔒 in the tab bar). Closing the window closes the rest; the locked
ones keep running, and the next =guiltty= brings that window back with
them, where you left them. Since v0.13.0 that's per window: each closed
window that kept locked tabs comes back as itself (chapter 21).
=Tabs= keeps the set of locked tabs, since it already owns the tab list,
and sends it to its window with the list; the Window only draws the lock
and, on close, calls =Tabs.close_unlocked/1=.

(Until v0.7.0 every tab was kept, always, and that surprised the user: a
new window opened wherever the old shells had been left, because they were
the same shells. One limit: if =Tabs= itself crashes, it takes back the
running sessions but forgets which were locked.)

#+begin_example
  $ guiltty                 the C client (chapter 23):
                              nobody on the socket? start the release as a
                                daemon: it opens its first window itself
                              running? "open" over the socket -> Launcher
  ... work in three tabs ...
  close the window          Window stops normally; its desk's Tabs and
                              locked sessions run on, windowless
  $ guiltty                 running: Launcher -> Lifeline.open -> that desk
                              gets a new Window -> Tabs.attach_window -> the same tabs
#+end_example

The =guiltty= command is a small C client that talks to the running node
over a Unix socket ([[file:23-client-server.org][chapter 23]]). A node it starts opens its first window
as it boots, on the display it inherited. A node already running is asked
for a window: the caller's =DISPLAY= (and Wayland, XAUTHORITY) travel with
the request, so the window opens on the display you ran =guiltty= from.
Since v0.13.0 it's a closed window that kept locked tabs, if there is one,
and otherwise a new window with its own tabs.

(Until v0.15.0 the launcher was a shell script, =rel/env.sh.eex=, that
asked over Erlang distribution: every launch booted a second VM to ask,
and closing a window during a launch could fail it. Chapter 23 tells
that story.)

* Backpressure, end to end

#+begin_example
   cat bigfile
      | write()          blocks when the PTY buffer is full
   kernel PTY buffer
      | read()           only while < 4 chunks are unacknowledged
   Pty  --{:pty_data}--> Parser --Screen.apply (call)--> Screen
     ^                     |                               |
     `------ Pty.ack ------'                {:screen_dirty} once
                                                           v
   renderer <--ROWS-- Window --Screen.take_update-------  (pull)
       |                ^
       `---- FRAME -----'   the next update only after the frame is drawn
#+end_example

Two kinds of flow control meet here:

- *Credit-based* between Pty and Parser: the Pty reads only while fewer than
  4 chunks are unacknowledged. When it stops reading, the kernel's PTY
  buffer fills and =cat='s own =write()= blocks. The kernel throttles the
  program to guiltty's speed, and nothing piles up in memory. A test floods
  2.6 MB through a shell and samples the parser's mailbox: never more than 4.
- *Pull-based* between Screen and Window: the Screen says "dirty" once and
  keeps collecting changes; the Window takes one combined update per frame.
  33 chunks of =seq= output became 13 frames.

Measured on this machine: a 101 MB =cat= in one tab took 6.3 s (about
16 MB/s, the parser's speed), and meanwhile another tab answered commands
in 6 ms.

* Config as code

=~/.config/guiltty/config.exs= (or =$GUILTTY_CONFIG=) is plain Elixir:

#+begin_src elixir
[
  font: [family: "monospace", size: 18],
  theme: [fg: "#c5c8c6", bg: "#1d1f21", cursor: "#c5c8c6",
          ansi: ~w(#1d1f21 #cc6666 ... #eaeaea)],
  keys: [new_tab: ["ctrl+shift+t"], close_tab: ["ctrl+shift+w"]]
]
#+end_src

[[file:../lib/guiltty/config.ex][Guiltty.Config]] checks the file's modification time every second. On a
change it evaluates the file in a separate, *monitored but not linked*
process (a config that raises can't take Config down; an earlier version
used =Task.async=, which links, and a test caught it), validates it, and
sends ={:config, config}= to the Window:

- a theme: the renderer gets the new 259 colors, then every row again
  (it had resolved them with the old theme);
- a font: the renderer rebuilds its atlas, the cell size changes, the grid
  changes, and a RESIZE goes out;
- keys: the Window re-reads its bindings.

A broken file is ignored and the previous config stays; the error goes
to the log, and a one-line version to the window (chapter 16). The
example is [[file:../priv/config.example.exs][priv/config.example.exs]]. Every setting, and how each one
reaches the shell or the pixels, is in [[file:16-config.org][the configuration chapter]].

* Questions

1. Why isn't the Window significant, when it was in MVP 1?
2. After a parser is killed, why does the Pty send SIGWINCH?
3. What makes =cat= slow down when guiltty can't keep up?
4. Why does the Window wait for a FRAME before taking the next update?
5. Why evaluate the config in a monitored, unlinked process?
6. Why does the Keeper exist? Couldn't =Tabs= keep its table by itself?
7. Hibernating an idle Screen freed its heap but not its rows. Why?
8. Observer runs outside guiltty. Why does guiltty still need
   =runtime_tools=?

** Answers
:PROPERTIES:
:VISIBILITY: folded
:END:

1. In MVP 1 closing the window meant quitting. Now the tabs outlive
   windows, so closing one must not stop guiltty.
2. The killed parser lost the bytes it was holding. Full-screen programs
   redraw everything on SIGWINCH, repairing the screen.
3. The Pty stops reading, the kernel's PTY buffer fills, and =cat='s
   =write()= blocks until there's room.
4. Without it, a fast program would queue updates faster than the renderer
   draws them. One update per frame keeps memory flat and latency low.
5. A linked process that raises takes its caller down. A monitor only
   reports the death, so a config that raises can't crash guiltty. (A
   config is still code that runs as you: one that calls =System.halt/0=
   does stop guiltty.)
6. A table dies with its owner unless it has an heir, and the heir has to
   be a process that outlives the owner. The Keeper is that process; it
   holds the table only while no =Tabs= does.
7. The rows are refcounted binaries outside the heap, and they're live:
   they are the scrollback. Hibernating frees only what's garbage.
8. Observer collects its data by calling =observer_backend= on the node
   it shows, so that module has to be in guiltty's code, not only in
   Observer's Erlang.
